# RTX 3090 Ti 解说视频：模型参数轻量调整方案

**版本：2026-09-24｜适用：Windows、单张 RTX 3090 Ti 24GB、local_drama_studio**

## 1. 决策摘要

**继续使用现有模型组合。优先改善旁白的一致性与完整性；图像、文本的现有配置以保留为主。**

本方案结合你提供的《解说视频（解说工厂）模型与参数配置清单》、项目源码，以及官方文档、GitHub Issues、Hugging Face 和 Reddit 的第一手社区记录编写。项目源码核对基准为 [d91a4107](https://github.com/Qioooba/local_drama_studio/tree/d91a4107b6733a4783d860689fb819720463214a)。你清单中的 Windows 运行结果视为你提供的实测；本次没有在你的 3090 Ti 上重新执行模型。

本轮交付的是参数与实施方案。涉及当前状态的判断，以实际启动日志、锁定模型和生效工作流为准；清单里尚未提交的本地修改可能与公开提交不同。

| 环节 | 建议的常规起点 | 需要调整的条件 |
|---|---|---|
| 文本 Qwen3.8-27B UD-Q4_K_M | **保留 ctx 150000、K/V q4_0、MTP 2、单并发** | 实际 OOM、持续进入共享内存，或只做短文解说时，再单独试 ctx 65536 |
| 图像 Qwen-Image-2.1 | **保留 INT8 ConvRot、20 步、CFG 1、Euler/simple、batch 1** | 同镜头 20/25 步对照后，质量改善明确才升到 25；复杂关键帧按需 40 |
| 配音 VoxCPM2 | **固定参考声音；max_len 192→256；暂保留 4 步、cfg 2** | 对照 4/10 步；10 步明显提高可用率才作为生产默认 |
| 配音组织 | **同一原始参考音频；自然句段约 15–25 秒；顺序批处理** | 音色漂移、长段加速、尾句不完整时优先检查这里 |
| ASR / 对齐 | **保留 1.7B ASR + 0.6B ForcedAligner；ASR 上限 128→512** | 先保证独立转写、字段和时间单位接通，参数才有实际意义 |
| 视觉质检 | **复用现有 27B + mmproj** | 接通既有质检能力后使用；真实显存不足才减少每批图片 |
| H3 视频 | **仅作少量短镜头的独立试验，保留已跑通工作流** | 有明确运动需求再测，不作为解说主链完成的前提 |
| 运行环境 | **保留现有两个 ComfyUI 环境和已验证版本** | 具体故障有对应上游修复，或独立对照证明收益时再升级 |

表中的“常规起点”是本项目建议，不能理解为官方公布的“3090 Ti 最优参数”。本轮最少的开发集中在**配音调用**与**独立 ASR/对齐接线**两组；图像和文本主要使用现有配置入口。

## 2. 文本：现有 150K 配置并非明显不合理

### 2.1 本轮查到的直接 3090 Ti 证据

社区贡献者 @hypertectonic 报告了 Qwen3.8-27B Q4_K_M 的同机对照：

| 服务器上下文上限 | 关闭 MTP | MTP 草稿数 2 | 开启 MTP 后加载显存 |
|---|---:|---:|---:|
| 128K | 42.0 token/s | 60.9 token/s | 20,134 MiB |
| 256K | 41.2 token/s | 61.4 token/s | 23,718 MiB |

条件为 RTX 3090 Ti 24GB、Linux/CUDA、llama.cpp `62bf73d`、K/V q4_0、单并发、thinking 关闭；三种提示各跑三次、丢弃预热，同一上下文下只改变 MTP。**表中 128K/256K 是分配上限，测速输入很短，不是塞满这些长度后的速度。** 测试日期未注明，2026-09-24 核验。[原始记录与方法](https://github.com/sudoingX/qwen38-mtp)

这支持保留你的路线，却不能承诺 Windows `b10689`、UD-Q4_K_M、带 mmproj 的服务也有相同速度。尤其 256K 档加载后只剩少量显存，不适合据此把你的上限继续提高。

另一个 RTX 3090 作者的 UD-Q4_K_XL 测试中，MTP 2/3/4 的散文速度分别为 **41.5/37.8/35.1 token/s**，而混合任务平均值却是 MTP 3 更高。解说稿更应关注散文表现，所以**保留 MTP 2**，不用追随混合榜单改为 3 或 4。该测试为 250W、131072 上限、q4_0、llama.cpp b10473；具体测试日期未注明。[3090 分任务记录](https://github.com/sudoingX/qwen38-mtp/blob/master/sweeps/rtx-3090.md)

### 2.2 逐项参数建议

| 参数 | 当前值 / 建议 | 理由 |
|---|---|---|
| 模型量化 | 保留 UD-Q4_K_M | 已在用；没有同业务证据要求改 Q5/Q6 或更低量化 |
| `llama_ctx_size` | 保留 **150000** | 先看真实任务，而不是按显存容量武断缩小 |
| K/V cache | 保留 **q4_0 / q4_0** | 有同款卡可行记录；q8_0 留作针对性对照 |
| MTP | 开启，draft tokens **2** | 有直接同款卡对照支持 |
| GPU layers / Flash Attention | 保留 **99 / on** | 查看实际加载层数；99 是请求值，不代表模型恰好有 99 层 |
| 并发 | **1** | 单用户、单卡阶段互斥，不追求并发吞吐 |
| batch / ubatch | 保留 **2048 / 512** | 没有本机瓶颈证据时不扩大 ubatch |
| fit / fit-target | 保留 **on / 768** | 不把自动适配当作必然避免所有 OOM 的保证 |
| mmproj | 保留现有 F16 文件 | 后续视觉质检要用，纯文本跑分省掉它的条件不能直接迁移 |
| 启动 / 空闲回收 | 保留 **180 秒 / 300 秒** | 已有协调与回收流程；不另建常驻服务 |
| 文本采样 | 保留 **temperature 0.2、top_p 0.9、JSON Schema、thinking off** | 适合当前结构化解说流程；已有代码显式关闭 thinking |

本项目这些设置的入口与生效路径见 [Settings](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/config.py)、[llama-server 管理器](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/infrastructure/llama_server_manager.py)、[文本调用适配](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/infrastructure/local_llm.py)。llama.cpp 的 fit 行为及参数边界见 [官方 server 文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)。

**什么时候才试 65536？** 出现 OOM、明显权重卸载/共享内存持续增长，或者确定这个服务只做短文解说、不再需要长材料时，先只改上下文上限，比较真实任务的首字延迟、总耗时和完整性。若同一网关还用于长文工作，保留 150K 更合适。不要同时改 ctx、KV、MTP 和 batch，否则无法判断哪项产生影响。

“上下文调小”不等于“实际输入变短”，也不保证生成必然加速。输入预算须包含系统提示、素材、结构化输出余量，以及视觉输入占用。代码中的各阶段 `num_ctx` 在当前 llama.cpp 客户端没有作为独立上下文上限发送；真正的服务上限来自启动参数 `-c`。[项目客户端实现](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/infrastructure/local_llm.py)

研究计划 max_tokens 1200、事实/讲稿 16000、分镜 14000 先保留。它们是输出上限，不会强制每次写满。若输出不完整，先检查终止原因和 JSON 完整性；无需为了“省显存”一律压到 2048。[当前文本规划器](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/explainers/text_planner.py)

## 3. 图像：守住 INT8 基线，做一次有针对性的步数对照

### 3.1 保留项与少量可调项

| 参数 | 常规使用 | 可选对照 |
|---|---|---|
| DiT / 编码器 / VAE | 现有 INT8 ConvRot / INT8 ConvRot / BF16 | 本轮不换量化文件 |
| steps | **20** | 25；关键难图才试 40 |
| CFG | **1.0** | 本轮不调 |
| sampler / scheduler | **euler / simple** | 本轮不加 shift 或自定义调度节点 |
| denoise / batch | **1.0 / 1** | 保持 |
| 负向提示 | 保持空 | CFG 1 下常规负向引导分支被跳过，堆负向词不是主要改进手段 |
| 480p 横屏模型画布 | **864×480** | 对应版画布 854×480 的对齐处理 |
| 480p 竖屏模型画布 | **480×864** | 此处是解说 T2I 路线；不要混用 H3 档位的 480×832 |
| 参考图编码 resolution | **1024** | 这是参考图预处理尺寸预算，不是纯 T2I 的输出分辨率 |
| seed | 保留当前确定性派生 | 同一次步数对照固定同 seed |
| 超时 | **600 秒** | 先区分冷启动、编辑和大图，再决定是否延长 |

官方 Qwen 管线给出 40 步；Comfy 官方 T2I 模板采用 25 步、CFG 1、Euler/simple。两者提供质量对照起点，不能据此认定你当前的 20 步错误。[Qwen 模型卡](https://huggingface.co/Qwen/Qwen-Image-2.1)、[Comfy 固定版本模板](https://github.com/Comfy-Org/workflow_templates/blob/371a7b7171bbd11e9cc92ef615ba5ad223d7e5b4/templates/image_qwen_image_2_1_t2i.json)

画布与节点语义分别核对了 [项目画面生成代码](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/explainers/picture_generation.py)、[Comfy Qwen 节点](https://github.com/Comfy-Org/ComfyUI/blob/6bfaacc67c2103481e5f0c84d75257cd0581d86a/comfy_extras/nodes_qwen.py) 和 [采样代码](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/samplers.py)。

**对照只需 3 个镜头、6 张图。** 选单主体、多人/复杂空间、容易画错的物体关系各一个；固定提示、种子、尺寸，仅比较 20/25 步。按实际成片显示尺寸判断主体、构图与细节。如果看不出稳定改善，保留 20。增加步数不能保证解决错误提示、人物身份或构图问题。

封面或较清晰源图可以在已有图像工具里单独试 **1376×768 / 768×1376**；这属于单图质量对照，不改变整个视频流水线的生成高度。当前公开代码的 1080 交付配置并不代表已接通真正的超分处理，本轮也不以新增超分模型为前提。

### 3.2 社区记录给出的实际启示

**最有价值的是一个性能结论反转的复盘。** RTX 5060 Ti 16GB 用户在 Windows、Comfy 0.37.0、1760×2368、20 步下，最初报告 INT8 热跑 234/267 秒，GGUF Q8 为 158/158 秒。维护者指出需要 cu130；作者 9 月 24 日升级补测后，INT8 为 75/76 秒。这个个案说明要先确认实际运行内核，不能只按文件格式判断快慢。[9 月 22 日维护者回复](https://github.com/Comfy-Org/ComfyUI/issues/16470#issuecomment-5779280565)、[9 月 24 日作者补测](https://github.com/Comfy-Org/ComfyUI/issues/16470#issuecomment-5814691302)

你的清单已经是 cu130，当前性能正常便保留。上面是 5060 Ti 的数据，不是给你的 3090 Ti 设定的速度目标。另一位 4060 Ti 16GB 用户报告双 INT8 ConvRot 可运行，但没写尺寸、步数和完整环境，只能作可行性旁证。[HF 第一手讨论 #35](https://huggingface.co/Qwen/Qwen-Image-2.1/discussions/35)

8189 保留 `--disable-dynamic-vram --reserve-vram 1`。这里的 reserve 是预留显存量，不是质量参数；关闭 dynamic VRAM 也不是所有 3090 Ti 的通用最优解，只是你已经跑通的基线。[Comfy 参数定义](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/cli_args.py)

SageAttention、TeaCache、Spectrum、torch.compile 暂不加入常规方案：本轮未找到与你当前模型、Windows 环境、尺寸一致且同时交代质量的 3090 Ti 对照，无法证明这些改动值得增加维护成本。调度器也保持 simple；Comfy 维护者对 Qwen2.1 的固定 shift 解释为压制网格纹的有意选择，社区仍有质量分歧，不应把另一个调度器当成必须安装的修复。[调度讨论 #16447](https://github.com/Comfy-Org/ComfyUI/issues/16447)

### 3.3 现有 2512 备选单独保留参数

如果使用已安装的 Qwen-Image-2512 Q5_K_M，沿用其独立 Profile，不继承 2.1 的 CFG 1。可用 **40 步、CFG 4、Euler、batch 1、denoise 1** 作对照起点，scheduler 保持该 Profile 原值；20 步用于预览，50 步作官方基线比较。40 步取自量化作者工作流，CFG 4 取自官方示例，均不是本机验证出的最优值。[2512 官方示例](https://huggingface.co/Qwen/Qwen-Image-2512)、[Unsloth 工作流说明](https://unsloth.ai/docs/models/tutorials/qwen-image-2512)

**许可需修正一种过宽的理解。** Qwen 官方 9 月 21 日说明，生成输出不属于许可中的 Materials，用户保留对输出的权利；模型文件当前仍使用 9 月 20 日的 Research License，商业使用模型本身的条款另有要求。不要把这两层直接简化成“生成图片一律不能商用”，也不要把输出权利声明当成无限制商业部署授权。本轮不据此自动更改项目授权记录或导出判定。[官方输出权利说明](https://x.com/QwenDevs/status/2101917379785838660)、[当前许可文本](https://huggingface.co/Qwen/Qwen-Image-2.1/blob/main/LICENSE)

## 4. 配音：这一部分最值得先改

### 4.1 固定参考声音，比增加采样步数优先

全片选同一段 **10–20 秒、干净、单人、语速自然**的参考录音，每个句段都复用原文件。这个范围是从官方建议的 5–30 秒中选取的实际起点。无参考时，上游明确提示不同调用可能出现不同声音；长文本也建议拆段。[VoxCPM 使用指南](https://voxcpm.readthedocs.io/en/latest/usage_guide.html)

本轮优先使用现有接口能够表达的 **prompt_wav_path + 准确匹配的 prompt_text**，采用续接式克隆，让声音和讲述方式稳定。官方 HiFi/Ultimate 完整示例还同时传入 `reference_wav_path`，与只传前两项不完全相同。若以后需要逐句情绪控制，再评估相应的可控克隆模式。维护者确认过 Ultimate 不响应同样的风格控制，所以不能假定一个数值 speed 参数会生效。[模式差异讨论 #210](https://github.com/OpenBMB/VoxCPM/issues/210)

项目当前通过 `inspect.signature(model.generate)` 检查显式参数，但当前上游公开封装是 `*args, **kwargs`，会导致支持的参考参数被误判。**先按实际锁定的 VoxCPM 版本修正这一小段调用，再启用固定参考。** 同时把 `speed_applied_natively` 改为转发真实结果，常规 speech_rate 先保持 1.0。[上游封装](https://github.com/OpenBMB/VoxCPM/blob/main/src/voxcpm/core.py)、[项目运行脚本](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/scripts/local_ai_runtime.py)、[项目适配器](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/explainers/runtime_adapters.py)

**参考声音的实际落点：**现有 `create_channel_profile` 接收 `version.voice.voice_ref`，保存为 `channel_profile_versions.voice_json.voice_ref`；作品通过 `current_channel_profile_version_id` 读取它。支持格式示例为 `voxcpm2:media:<参考录音媒体ID>|<准确参考文本>`，也支持参考文件路径；尖括号须替换为真实值。由开发者通过已有栏目配置创建和绑定流程设置，声线来源等字段沿用真实记录；当前 AudioPage 没有参考录音选择控件，本轮不要求新增音色管理页面，也不把 voice_ref 随意放进 runtime JSON。[配置创建与保存](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/explainers/production.py)、[声线快照读取](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/explainers/production_pipeline.py)

### 4.2 max_len 192→256：处理长句的余量

标准 VoxCPM2 配置的 patch_size 为 4，Audio VAE 解码倍率为 8×6×5×2×2×2=1920，输出采样率 48000。因此每个生成 patch 约对应 0.16 秒：

```text
max_len=192 → 192 × 0.16 = 30.72 秒
max_len=256 → 256 × 0.16 = 40.96 秒
```

这是**新生成音频的上限量级**，不是固定输出长度，也不是中文字数。模型遇到停止标记或其他长度限制会更早结束。推导来自 [官方模型配置](https://huggingface.co/openbmb/VoxCPM2/blob/main/config.json) 和 [生成循环](https://github.com/OpenBMB/VoxCPM/blob/main/src/voxcpm/model/voxcpm2.py)。

建议每段按自然句组织，目标 **15–25 秒**，上限设 **256** 留余量。用你清单中的约 4.9 字符/秒只能做粗估，实际仍以音频为准；不按固定字符数在句子中间硬切。接近时长上限只是疑似截断信号，要听末句、看独立转写是否读完，不能以“WAV 非空”验收。

### 4.3 配音参数表

| 参数 | 建议值 | 实施说明 |
|---|---|---|
| `inference_timesteps` | 暂保留 **4** | 用同一批句段比较官方默认 **10**；不要凭感觉把 8 写成最优 |
| `cfg_value` | **2.0** | 显式记录，先不调 |
| `min_len` | **2** | 保留 |
| `max_len` | **256** | 单句与批量路径都要一致 |
| 参考录音 | 同一份 **10–20 秒**原始录音 | 配准确参考文本；全片复用 |
| `seed` | 每段稳定派生并记录 | 用于对照与复现；固定种子不能代替固定音色 |
| `normalize` | **False** | 口播中的数字、年份、型号先在确定文本中处理 |
| `denoise / load_denoiser` | **False / False** | 以干净参考为前提 |
| `optimize` | **False** | 保留当前可用 Windows 环境 |
| `retry_badcase` | 本轮先保留 **False** | 失败段用既有返工路径，不新建自动重试系统 |

上游当前默认步数为 10、cfg 为 2；4 步是允许的速度取向选择，并无充分证据证明它与 10 步质量完全相同。[官方 API](https://voxcpm.readthedocs.io/en/latest/reference/api.html)

若以后只想启用模型自带的有限重试，可用 `retry_badcase=True, retry_badcase_max_times=2`，表示最多两次总尝试。但它只检测生成长度比例等 badcase，不能检查所有错读或漏读，耗尽后仍可能返回结果；不要再叠加不受限制的应用重试。[实际重试实现](https://github.com/OpenBMB/VoxCPM/blob/main/src/voxcpm/model/voxcpm2.py)

## 5. ASR、对齐和视觉质检：先确保检查真的发生

### 5.1 ASR 与对齐

继续使用 Qwen3-ASR-1.7B 和 ForcedAligner-0.6B。短句段 ASR 采用 **do_sample=False、max_new_tokens=512** 作为起点，替代当前脚本的 128。512 是输出上限，遇到结束标记会提前终止，不会固定生成 512 个 token。[ASR 官方生成配置](https://huggingface.co/Qwen/Qwen3-ASR-1.7B-hf/blob/main/generation_config.json)

ASR 对实际音频独立转写，再与确定口播文本比较。ForcedAligner 负责把已知文字放到时间线上；把正确稿件交给对齐器，不能证明配音没有漏读。现有字段、单位和独立 ASR 接线问题要先完成此前报告里的最小修正，避免参数变了但检查没有执行。[官方对齐用法](https://huggingface.co/Qwen/Qwen3-ForcedAligner-0.6B-hf)、[项目运行适配器](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/explainers/runtime_adapters.py)

交给开发者时，按以下三个具体落点处理即可：

- `production_pipeline.py` 的对齐调用当前传 `asr=None`，改为注入已有 LocalAsrAdapter；把 adapter 的 `transcription` 统一映射到消费者实际读取的 `text`。
- 批量输出 `text/start_time/end_time` 是秒，单段输出 `text/start_ms/end_ms` 是毫秒；在 adapter 边界统一为 `token/start_sample/end_sample/sample_rate_hz`。例如 48kHz 下段内 0.16 秒对应 7680 sample；段落偏移只在既有约定位置加一次，不能把 160ms 直接写成 160 sample。
- `narration_align.py` 消费统一后的词级时间；`production_pipeline.py` 字幕构建采用这些时间。不能只创建一个 alignment revision 后，仍按字符比例分摊整段时长。

这些是现有端口的字段与单位修正，不要求引入新对齐模型或中间服务。[当前对齐消费者](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/worker_handlers/narration_align.py)、[批量对齐与字幕构建](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/explainers/production_pipeline.py)

中文解说先沿用 Chinese；英文段按实际语言传入，不用 Chinese 处理所有语言。输出沿用现有 48kHz 合成时间基准，模型预处理按官方要求重采样。该 aligner 配置的时间栅格为 80ms，不应在验收文档中写成采样点级精确字幕。[时间配置](https://huggingface.co/Qwen/Qwen3-ForcedAligner-0.6B/blob/main/config.json)

### 5.2 可选：视觉质检

按你提供的清单，当前没有已发布的 QC_VISUAL Profile。本轮若启用自动审片，为现有 Qwen3.8-27B 与 mmproj 配置并发布该 Profile，复用已有 provider，接入图片和预期依据；若本轮不启用，则保持未检查并人工看图。当前代码的参数 **temperature 0.1、top_p 0.9、max_tokens 2500、每批上限 6 帧** 可以保留；真实多图调用显存不足时再降为每批 2 帧或 1 帧。这里的批大小属于现有 provider 构造参数，不假装它已经是页面设置。[当前视觉质检实现](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/explainers/visual_qc.py)

没有传入可用图片、缺少判断依据或模型未执行时，应保留“未检查”状态。这是启用自动审片的前置正确性要求；不通过换一个更大的视觉模型解决接线问题。

## 6. H3：可选短镜头试验，先核对真正生效的参数

当前解说主链的 I2V 尚未实际执行。H3 放在单独试验范围，先做一个人物小动作镜头、一个环境轻运动镜头，各取 4–5 秒可用素材。[解说生产代码](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/explainers/production_pipeline.py)

**项目当前 H3 参数与清单概述有一处需要更新：** 默认 `use_production_tier=True`，DRAFT 档是 **107 帧、24fps、20 步、denoise 0.97**；横屏 864×480、竖屏 480×832。自由模式才把 `sigma_points` 直接传给 `BasicScheduler.steps`，所以在这条项目链里它实际表示步数，并不是“减 1 后才是步数”的普通 sigma 数组长度。档位开启时，修改自由 Sigma 字段不会改变实际步数。[H3 工作流编译器](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/h3_workflows.py)、[字段生效条件](https://github.com/Qioooba/local_drama_studio/blob/d91a4107b6733a4783d860689fb819720463214a/apps/api/local_drama/application/workflow_definitions.py)

先保留当前可用的 INT8ConvRot 路线、默认加速 OFF 和现有采样节点。不要因为已经安装 `minimax_h3_turbo_v4_step600_ema.safetensors` 就直接把默认工作流压到 4 步。Larry 原作者建议 6–8 步并要求匹配其节点与 sampler；项目当前使用 KSamplerSelect(res_multistep) + BasicScheduler + SamplerCustomAdvanced，未接入 Larry 的专用 sampler。[Larry 原作者模型卡](https://huggingface.co/larryvrh/MiniMax-H3-Turbo-Lora)

社区里确有 RTX 3090 24GB、128GB 系统 RAM、FL2VA INT8、544×800、5 秒、20 步的作者实测：第二次运行采样 142.6 秒，总计 160.9 秒。它使用 Ubuntu、cu130、Sage 等条件，且基础模型路线不同，不能承诺你的 Windows REF2VA 获得相同时间；原帖绝对日期未核实，2026-09-24 核验。[作者原帖](https://www.reddit.com/r/comfyui/comments/1vgcr5u/minimax_h3_i2va_generation_rtx5090_vs_rtx3090_vs/)

如果默认档已满意，本轮到此停止。只有仍需加速时，才在独立 Comfy 工作流中试**匹配基础模型、LoRA、节点的官方 8-step 模板**，不是只替换一个文件。Comfy 新模板中的 FL2V 与 Ref2V Turbo 也各有对应文件。[Comfy 官方 H3 本地模板](https://docs.comfy.org/tutorials/video/minimax/minimax-h3-native)

项目现有 REF2VA 节点可能要求 Audio VAE，直接关闭原生音频会被拒绝；解说成片是否采用其音轨在合成时决定，避免未经审核的原生人声与旁白重叠。先保留已跑通的生成条件，不为静音需求破坏节点输入。

## 7. 最小实施清单

### 7.1 直接可用的现有配置

图像步数只有在对照确认值得后才改为 25。以下是**合并到现有 config/config.json 的 runtime 对象的字段示例**，不是完整配置文件：

```json
{
  "explainer_generation_steps": 25
}
```

回退值是 20。它是当前确实支持的设置键；无需新增页面或模型注册机制。

只在第 2 节列出的条件发生时，另做一次上下文回退试验：

```json
{
  "llama_ctx_size": 65536
}
```

回退至原值 150000。保留其余 runtime 字段，通过现有服务管理流程重启，并查看**真正启动命令里的 -c 和实际生效模型**。你清单还有 ACTIVE 运行时记录，不能只凭某一份 JSON 已保存就认定服务已经切换。

### 7.2 两组小改动

| 优先级 | 修改位置 | 交付内容 | 完成标准 |
|---|---|---|---|
| 第一组：配音 | scripts/local_ai_runtime.py、现有 subprocess 参数转发、runtime_adapters.py | 单句/批量共用同一小段参数构造；max_len 256、cfg 2；固定参考参数正确通过；稳定 seed 与真实 speed 标记 | 同一参考可连续配多段，尾句完整；4/10 步确实到达模型；日志能看见实际参数 |
| 第二组：音频检查 | 当前 ASR / alignment 适配与消费位置 | ASR 上限 512；独立转写接通；结果字段与秒/采样偏移单位一致 | 故意漏掉一句的音频不能通过“全文一致”；字幕时间落在实际音频范围内 |

为了以后做 4/10 步对照，**最多新增两个机器设置键**即可，例如 `explainer_tts_inference_timesteps` 和 `explainer_tts_max_len`，接入现有 Settings 与 subprocess；名称在此是拟议设计，**当前代码尚不支持，不能直接写进 JSON 就期待生效**。其余值用现有模式或明确常量即可；不要新增数据库表、配置中心或调参后台。

视觉 QC 若本轮同时启用，修复“未执行却当通过”的前置问题，复用既有 Profile 和 provider。完整缺陷范围仍以此前源码复核文档为准，本方案不展开另一轮重构。

### 7.3 本轮到这里为止

保留单卡按阶段互斥、一次加载后顺序批处理、现有 FFmpeg 合成。H3 仅保留短镜头试验；动态语速、情绪控制、全链 1080 超分、编译加速、多进程并发，以及迁移 vLLM/另一套推理引擎，均等待实际需求或瓶颈后再考虑。社区存在更快引擎的榜单，但跨引擎成绩不能作为当前 llama.cpp 的参数目标。

## 8. 少量验收，够用就停止

按下面顺序执行，每次只改变一个影响结果的因素。每组记录模型/版本、参数、冷启动时间、热运行总时间、可用结果数量即可，用已有日志或一张表就够。

| 顺序 | 样本 | 改动 | 判定与回退 |
|---|---|---|---|
| 1. 配音接线 | 同参考、2–3 段真实中文 | 修参考输入与 max_len，不改步数 | 声线稳定、末句完整，记录实际时长；先解决正确性 |
| 2. 配音步数 | 6 个真实句段，每段分别跑 4/10，共 12 段 | 仅 inference_timesteps | 人名、年份、型号、停顿、长句；10 明显提高可用率才采用，否则留 4 |
| 3. 图像步数 | 3 个实际镜头，共 6 张 | 仅 20/25 | 看成片尺寸下的主体/构图/细节；改善不明确留 20，个别关键帧再试 40 |
| 4. 文本回退 | 仅在有明确问题时，3 个代表性请求 | 仅 150000/65536 | 输入与输出预算足够，首字和总耗时有实际改善才保留；否则回 150000 |
| 5. 短成片 | 1 条 3 分钟中文、单画幅解说，使用现有页面最短时长选项 | 使用已选定参数 | 无漏句，声线连贯，字幕跟随音频，静帧显示可接受 |
| 6. H3 可选 | 2 个短运动镜头 | 从已有可运行档开始 | 确有视觉收益且耗时可接受才采用；不影响前五项完成 |

配音比较时，固定同一原始参考、确定口播文本、每段 seed、cfg、max_len 与 optimize；把第一次加载单独记下。最终看“**获得一段可用旁白的总耗时**”，包含失败返工，而不是只比某一次推理速度。ASR 辅助找漏读，人工核听保留；模型给出的转写也可能出错。

**验收通过后，把选中的两三个值写回现有配置并保留旧值即可。** 本方案不预设必须换模型、升级运行时或增加一个新的管理系统。

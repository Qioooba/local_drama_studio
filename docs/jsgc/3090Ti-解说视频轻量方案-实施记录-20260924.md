## 2. 第一组：配音

### 2.1 固定参考声音原本被误判为“不支持”

`scripts/local_ai_runtime.py` 用 `inspect.signature(model.generate).parameters` 判断锁定的 VoxCPM 是否支持 `prompt_wav_path`。实际安装的封装是：

```python
# F:\AI_Models\LocalDramaStudio\Runtimes\QwenVox\site-packages\voxcpm\core.py
def generate(self, *args, **kwargs) -> np.ndarray:
    return next_and_close(self._generate(*args, streaming=False, **kwargs))

def _generate(self, text, prompt_wav_path=None, prompt_text=None,
              reference_wav_path=None, cfg_value=2.0, inference_timesteps=10,
              min_len=2, max_len=4096, ...):
```

`generate` 只声明 `*args, **kwargs`，所以参数名检查看不到任何显式参数，代码判定“缺少 `prompt_wav_path`”并抛 `VOXCPM_PROMPT_UNSUPPORTED`——**固定参考声音这条路根本走不通**。

**改法**：新增 `_generate_parameters()` / `_supports()`，把 `**kwargs` 视为“声明转发任意关键字参数”，因此 `prompt_wav_path`、`prompt_text`、`cfg_value` 都被判定为可用。检查的是真实锁定版本，没有放宽到“无条件传递”。

### 2.2 单一参数构造器

新增 `_voxcpm_generate_kwargs()`，单句（`_voxcpm_smoke`）与批量（`_voxcpm_batch`）共用。传入 `supports()` 回调，返回 `(kwargs, facts)`：

- `inference_timesteps` 默认 **4**（未改，方案结论是保留，只有对照实验才改）
- `max_len` **192 → 256**
- `cfg_value` 显式 **2.0**（原代码未传，依赖上游默认值）
- `min_len` 2、`retry_badcase` False（保留）
- `normalize` / `denoise` / `load_denoiser` / `optimize` 保持 False（保留）

`facts` 记录实际下发的每个参数，并写入执行回执（`parameters`）与每段 take 的 `generation_json.runtime_result.tts_parameters`，所以“4/10 步对照”能从产物里看出真实参数，而不是靠日志推断。

### 2.3 max_len 256 的余量说明

标准 VoxCPM2 的 `patch_size` 4、Audio VAE 解码倍率 1920、输出 48 kHz，因此一个 patch ≈ 0.16 秒：

```text
max_len=192 → 约 30.7 秒
max_len=256 → 约 41.0 秒
```

这是**新生成音频的上限量级**，不是固定输出长度，也不是中文字数。按方案要求，段落仍按自然句组织（目标 15–25 秒），不在句子中间按字符数硬切。

### 2.4 `speed_applied_natively` 改为转发真实结果

原实现有三处硬编码 `True`，会让调用方以为语速已由模型原生处理：

| 位置 | 原值 | 现值 |
|---|---|---|
| `runtime_adapters.LocalAiNarrationTtsRuntime.synthesize` | 硬编码 `True` | 转发 subprocess 回执的真实值 |
| `narration_tts.py` 批量分支 `pre_synthesized` | 硬编码 `True` | 取批量每段回执的真实值 |
| `local_ai_runtime.py` 两个 TTS 任务 | 已在计算但只用于自身回执 | 经 `facts` 一路向上传递 |

锁定的 VoxCPM2 没有原生 `speed`/`speech_rate`/`rate` 参数，所以真实值恒为 `false`；`requested_speech_rate` 目前仍是 1.0，行为不变，但**一旦有人把语速调到 1.0 以外，调用方能正确判断需要自己走 atempo 后处理，而不是被误导跳过**。

批量路径新增 `pre_synthesized_receipt` 参数，把批量任务的每段回执（`speed_applied_natively`、`requested_speed`、`parameters`）带进 take 记录。

### 2.5 两个新机器设置键

按方案 7.2 的“最多新增两个机器设置键”实现：

```json
{
  "runtime": {
    "explainer_tts_inference_timesteps": 4,
    "explainer_tts_max_len": 256
  }
}
```

- 默认值即方案建议的常规起点，因此**现有 `config/config.json` 无需修改**（当前 `explainer_generation_steps` 已是 20，也无需改动）。
- 键名与语义：`explainer_tts_inference_timesteps` 供 4/10 步对照，`explainer_tts_max_len` 供长句余量对照。
- 接入路径：`bootstrap/config_loader.py::RuntimeConfig` → `settings_values()` → `Settings` → `LocalAiSubprocessRuntime._narration_parameter_arguments()` → CLI `--inference-timesteps` / `--max-len`。单句与批量任务都收到同一组值。
- 支持环境变量覆盖：`LOCAL_DRAMA_EXPLAINER_TTS_INFERENCE_TIMESTEPS`、`LOCAL_DRAMA_EXPLAINER_TTS_MAX_LEN`。
- 未新增数据库表、配置中心或调参后台。

## 3. 第二组：音频检查

### 3.1 ASR 上限 128 → 512

`local_ai_runtime._asr_smoke` 的 `max_new_tokens` 由 128 改为 **512**（`DEFAULT_ASR_MAX_NEW_TOKENS`），并保持 `do_sample=False`。512 是输出上限，遇到结束标记会提前终止。原来的 128 足以在长句段被截断，而截断后的转写会被当成“这些字没读”去和讲稿比对。

回执新增 `max_new_tokens`、`do_sample` 字段；`local_ai_subprocess.transcribe` 显式传 `--asr-max-new-tokens 512`。

### 3.2 `transcription` → `text` 字段统一

`LocalAsrAdapter.transcribe` 原来只返回 `transcription`，而消费方 `run_narration_align_job` 读的是 `asr_result["text"]`：

```python
asr_text = normalize_for_alignment(str(asr_result.get("text") or ""))
```

结果是拿空串和讲稿比对。现在两个键同时带同一个值，`text` 为主键。

### 3.3 独立转写真正接通

`production_pipeline.make_narration_align_handler` 原来对每个 take 传 `asr=None`：

```python
asr=None,   # 旧
asr=asr_port,  # 新
```

新增 `_BatchAsr` 端口，把注入的真实 ASR 适配器包成对齐 Job 需要的形状。阶段回执新增：

```json
{ "asr_review_included": true, "asr_review_state": "WIRED" }
```

这样“独立转写没有发现问题”和“根本没有转写”在报告里不再无法区分。单独运行 `NARRATION_ALIGN` Job 的路径本来已注入 ASR，本轮未改其行为，只统一了字段。

### 3.4 对齐时间戳单位与字段统一

这是本轮发现的**第二个静默缺陷**，比方案描述更严重。

对齐模型（`processor_config.json`）的时间栅格是 **80 ms**，输入采样率 **16 kHz**，`decode_forced_alignment` 返回的是 `text` + `start_time`/`end_time`（**秒**）。而 `narration_align._match_chunks_to_tokens` 与 `_build_display_mapping` 读的是：

```python
start = chunk.get("start_sample", chunk.get("start_ms"))
word = str(chunk.get("word") or chunk.get("token") or "").strip()
```

管线里的批量路径（`runtime.align_batch`，一次加载、多段对齐）把对齐模型的原始字典**直接**塞进 `word_timings`：

- 没有 `token`，只有 `text` → 每个 chunk 被跳过
- 没有 `start_sample`/`start_ms`，只有 `start_time` → 每个 chunk 被跳过

于是所有 token 都变成“未对齐”，但 `run_narration_align_job` 依然写出一份 `ALIGNED` 修订，只是 `word_timings_json` 为空。**字幕时码因此完全没有对齐数据可用**。

**改法**：新增 `application/explainers/aligner_timestamps.py`，作为唯一转换点：

- `timestamp_samples()`：接受显式采样对、毫秒对或秒对；单位**绝不按数值大小猜测**，只按显式声明换算（0.160 秒在 16 kHz 下是 2560 samples，不是 160）
- `normalize_aligner_timestamps()`：把 chunk 规范化为 `token` + `start_sample` + `end_sample`，缺失的 chunk 直接不出现（由 handler 报为未对齐），`end < start` 抛错而不是静默重排

单段适配器（`LocalForcedAlignerAdapter`）与批量路径（`production_pipeline._BatchAligner`）共用这一个函数，不会再漂移。运行时脚本侧也统一了输出：`alignment` 与 `alignment-batch` 任务现在同时给出 `token`、`start_ms`/`end_ms`、`start_sample`/`end_sample`、`sample_rate_hz`，以及回执里的 `sample_rate_hz` 和 `timestamp_segment_ms`。

`sample_offset` 语义未改：当前约定是每个 take 内部从 0 开始，段落偏移只在既有位置（`narration_clips[].sample_start`）加一次，没有把 160 ms 写成 160 sample。

## 4. 顺带修复：字幕时码真正使用对齐时钟

方案 5.1 第三条明确要求，不能“只创建一个 alignment revision 后，仍按字符比例分摊整段时长”。实际代码正是如此：`make_subtitle_build_handler` 把 `narration_alignment_revision_ids` 写进字幕修订，却继续用等字符比例切分 cue。

**改法**（`production_pipeline.py`）：

- `_split_cue_chunks()`：切句/硬换行时保留每个 chunk 在 `display_text` 中的**字符偏移**（`_split_cue_text` 保留为兼容包装）
- `_display_map_span()` / `_aligned_cue_times()`：cue 的 `start_ms`/`end_ms` 优先取与其字符区间相交的 `display_map_json` 条目（sample → ms，按 take 采样率换算），裁剪到所属旁白片段范围内；没有对齐数据的 cue 才退回字符比例，且只在“未解析区间”内按序分配，保证时钟单调、整段边界精确落在片段边界
- 阶段回执新增 `cue_timing_source`（`ALIGNMENT_CLOCK` / `CHARACTER_PROPORTIONAL`）、`cues_from_alignment_segments`、`narration_segment_count`，以及每段的 `alignment_facts`（`word_timing_count`、`mapped_span_count`、`aligner_timestamp_grid_ms`）

`aligner_timestamp_grid_ms` 固定写入 80，用于在产物里留下“字幕时间量化到 80 ms 栅格、不是采样点级精确”的事实，避免验收文档写成采样点级精确。

## 6. 仍待人工执行的对照实验

代码已就绪，但方案 §8 的对照必须由人在本机跑，本轮不代为给出结论：

1. **配音接线**：同一参考 + 2–3 段真实中文，确认声线稳定、尾句完整。修好参考参数后这是**第一次真正可用**的固定参考路径，必须先跑通正确性。
2. **配音步数**：把 `explainer_tts_inference_timesteps` 改 4/10，各 6 段，比较人名、年份、型号、停顿、长句；10 步明显提高可用率才采用。
3. **图像步数**：`explainer_generation_steps` 20/25，3 镜头 6 张图，看成片尺寸下的主体/构图/细节；改善不明确就留 20。
4. **文本回退**：仅在有明确 OOM/共享内存增长时试 `llama_ctx_size` 65536，且一次只改一项。
5. **短成片**：1 条约 3 分钟中文单画幅，检查无漏句、声线连贯、字幕跟随音频。
6. **H3**：仅在有明确运动需求时做 2 个短运动镜头试验。

判据提醒（来自方案）：ASR 只辅助找漏读，人工核听保留；验收看“获得一段可用旁白的总耗时”，而不是单次推理速度。

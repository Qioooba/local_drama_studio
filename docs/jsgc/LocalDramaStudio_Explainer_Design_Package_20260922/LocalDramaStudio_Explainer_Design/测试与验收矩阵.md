# 解说工厂：测试与验收矩阵

版本：1.0　设计基线：《解说工厂完整设计与开发规范》1.0。源码参考快照：`8a63c604a1a13556dbe277d312ecf73bebb52883`。

**本文件是交给实施 AI 和测试人员的执行规范，共 90 条用例；本轮未运行产品、未调用用户 GPU、未生成真实成片。全部当前结果为 `NOT_RUN`。任何阈值都是拟定验收要求，不是已有成绩。**

测试对象是一次完整交付的解说工厂，包括真实本地生成、六个工作页、资料证据、长片、多语、恢复、审片、发布包以及原短剧兼容。测试顺序表示依赖，不表示把功能推迟到以后。

## 1 执行规则与证据口径

### 1.1 执行前必须冻结

每次验收创建唯一 `acceptance_run_id`，记录 Git commit、数据库迁移版本、操作系统、驱动/CUDA、CPU/内存/GPU、FFmpeg/字体版本、模型完整标识及哈希、量化版本、ComfyUI 与节点版本、工作流哈希、栏目版本、规则版本、语言/画幅/帧率和出站策略。模型锁文件只能作为预期，须另记文件校验、加载、能力探测和真实 smoke 结果。

所有断电、OOM、磁盘满、恶意文件、多 Worker 等测试仅针对专用测试进程、数据库副本和隔离目录。故障前保留备份。使用受控 HTTP 服务与出站记录器验证恶意请求，不以访问真实云元数据或第三方敏感服务作为证据。

通用步骤：准备输入 → 记录初始 revision/hash → 执行动作 → 等待有超时上限的终态 → 核对 API/数据库/真实文件/界面 → 保存日志和产物 → 判定。不能用固定等待几秒代替任务状态检查。生成已提交、HTTP 200/202、出现文件名均不等于制作成功。

### 1.2 层级和结果

| 标记 | 层级 | 可证明的范围 |
|---|---|---|
| U | 单元 | 纯规则、时间换算、状态与依赖算法；不证明模型质量 |
| C | 合同 | HTTP/schema/事件/adapter 合同；mock 结果必须标明 |
| I | 集成 | 真实数据库、文件、FFmpeg、解析器及服务协作 |
| E | 浏览器端到端 | 真实页面入口、操作、跳转、可用性；不以直接 API 调用代替应测试的点击 |
| G | 本地模型/GPU | 真实权重、工作流、参考图消费、声音与媒体生成 |
| F | 故障与并发 | 受控断进程、超时、OOM、重复提交、租约竞争 |
| M | 媒体审查 | 解码、帧/采样/PTS、响度、字幕、安全区和语义覆盖 |
| H | 人工标注/审查 | 听读真值、角色与史实复核、画面/交互审查；必须记录实际范围 |

未来执行可将结果改为 `PASS / FAIL / BLOCKED`，并填写证据链接、执行人/执行程序、执行时间、环境和缺陷编号；当前全部保持 `NOT_RUN`。`BLOCKED` 必须说明缺什么和如何补齐，不能用 mock 改写为 `PASS`。一行含多个条件时，证据必须逐项覆盖；只跑部分子项不能整行判通过。无平台发布授权不阻止验证手工交接，但不能据此声称自动上传已验证。

### 1.3 拟定门槛

核心事实冲突、旁白漏段、关键专名/数字错读、文件损坏、字幕使用过期文本、许可范围未满足均阻止发布包进入可发布状态。普通构图偏好和非关键审美问题可提示，不得触发无限重抽。

5 分钟自然叙事验收档为 285–315 秒；30 分钟档为 1710–1890 秒。精确时长模式另按总帧数验收：30 fps 的 300 秒为 9000 帧，1800 秒为 54000 帧；随附F07样片选择25 fps，中文精确300秒为7500帧。计划时码不等于实际音频时码。

人工标注的字幕边界偏差 P95 ≤150 ms；30 分钟末尾相对于 RenderManifest 统一时钟的差 ≤1 个输出帧。这是两个独立指标，不能用“各段误差不大”代替整片漂移检验。响度采用所选产品档，默认 -16 LUFS ±1、true peak ≤-1 dBTP；不是平台统一硬标准。所有指标保留原始测量值，禁止只输出一个 PASS。

## 5 真实 5 分钟样片验收流程

### 5.1 输入与运行

1. 冻结环境和模型能力，生成 `acceptance_run_id`。启用进程级出站记录；推理设 LOCAL_ONLY。选择已被核验适用于验收和拟定发布用途的素材/模型。H3 的全球授权未确认时，必须显示不满足全球发布，或在开始前选择已通过本机 smoke 的合适替代路径。
2. 清空本次项目的生成结果，从 UI 导入 F07，不能把外部已做好的视频放进目录冒充结果。保留完整文件、编码、hash、来源与明确虚构标记。确认 3 人物、2 场景、2 核心道具、24 段稿和40镜头计划均被识别；因真实配音调整分镜数/长度时，必须保留调整理由及新manifest。
3. 使用栏目快照，选择 AUTO_WITH_EXCEPTIONS、中文旁白、5分钟自然时长目标、横屏；同时请求英语配音版与中文配音双语字幕版。点击一次“检查并一键生成”，先冻结输入/策略/预算/任务骨架；预检无阻塞时自动提交，研究和TTS再合法展开子计划。测试者记录每一次介入的时间、原因、操作、耗时和影响范围，不能把“手工挑了全部候选”写成一键通过。
4. 系统实际完成本地稿件/实体、人物参考、语音/对齐、按真实时长分镜、图像/I2V、有限修复、混音字幕、渲染、QC与导出。F07 如有精确300秒计划，仅作初始计划；实际音频测出后依所选产品时长策略重排，禁止强行拉速、截句或静默改写锁定稿。双语烧录失败只有满足预授权及平台能力时才能改软字幕。
5. 自中文已确认版本生成竖屏输出，并保留横/竖构图、安全区和必要补画差异。英文版保留独立时轴；英文自然时长与中文不同不直接判失败，须满足其独立选择的输出目标且无语义删减。

| 画面技术 | 所有源片和全部输出全帧解码；检测黑场/帧数/PTS/尺寸与声明例外 | 每文件hash、总帧数、解码覆盖100%和异常说明 |
| 语义覆盖 | 实际跑首/中/尾、切点、状态变化点；至少对一段10秒镜头按实际帧率运行全帧深度模式（25fps为250帧，30fps为300帧） | 抽样与深度分别计数；明确剩余未逐帧理解的范围 |
| 音频 | 中文和英文旁白各完整听一次，检查专名数字、漏句、段间拼接和音乐压制 | 按segment逐条听审表、音轨与混音测量；人工审查耗时如实记录 |
| 字幕 | 逐cue对照当前稿，检查横竖和双语；对两种语言分布采样人工标注边界 | 全cue文本/越界报告，分语言P95/最大偏差以及标注真值 |
| 时长/时钟 | 根据选定自然/精确模式比较实际帧数、音频与最终cue | 中文自然档285–315秒；精确档满足总帧；尾部没有漏音/超尾字幕 |
| 交互 | 执行局部错读修复与一个镜头替换，查看其余hash | 修改可定位，只重跑必要依赖；六页截图和关键操作录屏 |
| 出口 | 解包所有要求的母版/字幕/音轨/封面/来源/QA/许可 | 导出hash绑定revision；全球许可不明不会进入可发布状态 |

自然产生的问题和人为注入的问题分开报告。修复后可判相应用例通过，但必须保存首次失败、修复过程、候选数及实际人工分钟，不能覆盖失败记录。“正常路径不用逐镜批准”的软件验收不等于“验证成片质量无需测试人员听审”。

## 6 真实 30 分钟长片验收流程

1. 使用 F08 独立长资料。从输入经真实本地生成产生约30分钟连贯作品；不允许循环5分钟样片、复制字幕、延长黑场或只用现成片段测试渲染就声称长链通过。TC-060 的精确时钟素材是渲染基准，不能替代TC-090的真实长片。
2. 记录计划与实际章节数、段数、镜头数、I2V比例、总帧数、分块数、生成配置、每阶段耗时、模型切换、峰值显存/内存/磁盘。按真实成本判断是否适合每日定时窗口；没有达到预期就提交差距与瓶颈，不补造一个“预计成功”的成绩。
3. 在已完成至少一部分真实素材后杀专用Worker一次；另选最终渲染时模拟一次可恢复故障。恢复后比较已验证成功产物hash，确认有效产物复用、无重复正式采用、没有全片重新生图。故障注入的暂停时间与生产净耗时分别统计。
4. 完成全部源片和最终片的全帧技术检查。对每个镜头跑已声明的语义规则，重点检查跨章回归角色、时间跨度服装、主要道具与结局；报告采样帧数/总帧数、具体区间及未检查项，不能将解码覆盖替换成语义覆盖。
5. 对最终中文音轨完整听审一次；英文版若纳入本次完整功能交付，也须提供真实英文音频与完整听审，不以中文通过代替。字幕对齐在开头、每章中段和结尾分布取样；每种语言至少50个人工标注边界，并完整核查所有核心专名数字。
6. 用manifest统一时钟计算每块开始/结束、每章边界及片尾误差；自然档总时长1710–1890秒，精确档按1800秒总帧验收。片尾presentation结束时刻误差≤1输出帧；AAC priming/padding和剪辑列表必须解释清楚。检查最后一句、最后一个cue和尾帧，防止“主体正常，片尾丢失”。
7. 导出至少一套中文横屏完整发布包和真实英文edition；做竖屏代表性复杂镜头验证后，若宣称该30分钟作品提供竖屏成片，必须实际完整导出并检查该文件，不能以几张截图冒充。各输出分别保留检查报告。
8. 复测源稿一处早段修改，确认后续绝对时码重新映射；复测只换BGM，确认画面源完全复用。最终交付修订前后manifest、失效图、真实新片和成本差异。

30分钟验收如因模型、驱动、许可、空间或耗时无法完成，必须交付失败位置、已完成有效产物、日志、环境与复现方式，状态为FAIL/BLOCKED。不能用“理论支持30分钟”“短片拼接验证成功”替代真实长链完成。

## 8 审查与修复闭环

代码审查要求检查：新增HTTP是否经过最终出站门禁；解说是否伪造Episode；机器是否可写人工批准或新增AUTO_APPROVE绕过旧工作流；输入是否能生成任意shell；导出是否冻结revision；多worker写入是否校验fencing；是否另建任务真源或仅靠内存；GPU等待是否占数据库事务；引用媒体是否同项目且版本真实；取消迟到结果是否仍能采用；schedule唯一键是否错误包含config_revision；运行内合法子计划是否误判自身stale；锁定稿/双语烧录是否被静默降级；OpenAPI客户端是否由规范生成。

每个缺陷记录 `issue_id → REQ → TC → 最小复现输入 → 实际/预期 → 证据 → 根因文件/函数 → 修复合同 → 受影响依赖 → 回归用例`。缺陷关闭须有失败复现和修复后实测，不能只有“代码已调整”。事实/身份/时钟/许可问题应阻止相关成片发布；审美问题按设定预算修复或留明确提示。

首次采用率、每镜头候选数、每成片分钟GPU耗时、每片人工分钟、渲染恢复复用率均公布分母和样本数量。工作流/栏目升级在固定F07及受影响的长片子集上对比；涉及时间轴、调度或共享渲染的改动须重跑30分钟及旧短剧回归。只改变文案排版或同类低影响项时，执行对应回归即可，不为制造测试数量重复整条GPU链。

**最终可称“完成”的条件：90条用例均有实际结果和证据；核心能力没有未解释FAIL/BLOCKED；5分钟与30分钟均有真实成片、审查范围和成本记录；旧功能回归成立；发布许可与账号能力按事实标示。没有实际执行的项目必须继续保持NOT_RUN。**

# 0. 本文的硬规则

本文不是“建议列表”，而是下一阶段重构时开发 Agent 必须遵守的架构合同。

## 0.1 六条不可违反的原则

1. **不另造第二套业务真值。** 现有 `shot_revisions`、`generation_variants`、`media_versions`、`selections`、`frame_anchors`、`shot_transition_constraints`、`jobs`、`automation_workflows`、`timeline_revisions` 等继续是事实来源。
2. **UI 可以大改，证据链不能推倒。** 用户看到的是更简单的导演台，但底层仍然必须可追溯、可复现、可审核。
3. **Agent 自动化只是业务编排层，不是第二套任务系统。** 自动生成每一集最终仍落到现有 durable `jobs` 与依赖关系中。
4. **模型选择按“能力”抽象，不按厂商写死页面。** 页面不应该让用户理解 ComfyUI workflow id、provider version、manifest 结构后才能生成。
5. **专业参数必须渐进披露。** 新手先看到“生成”“重抽”“锁定”“保持角色一致”；高级用户再展开 seed、采样、workflow、profile 等细节。
6. **重构按旁路替换（strangler）推进。** 任何阶段都必须能运行旧流程；禁止一次性改完 288 个接口、41 个迁移和全部 UI 后再首次联调。

## 0.2 开发 Agent 禁止自行发挥的事项

- 禁止新增另一套 `task_queue` / `generation_jobs` 来替代现有 Job。
- 禁止新增“最终图片路径”直接挂在 `shots` 上绕过 `media_versions`。
- 禁止覆盖旧 GenerationVariant；重新抽卡必须创建新 Variant。
- 禁止直接修改 frozen `shot_revisions`。
- 禁止用“QC 分数高”自动冒充人工审核通过。
- 禁止在前端偷偷回退模型而不告诉用户。
- 禁止把 `story_assets.canonical_media_version_id` 当作未来完整的角色一致性模型。
- 禁止把角色三视图塞进一个无结构 JSON 后就宣称“支持角色 Bible”。
- 禁止让创作用户手动复制 UUID / media version id / profile version id 完成正常工作流。
- 禁止为了“微服务化”拆网络服务。当前产品是 LOCAL_ONLY，本阶段采用**模块化单体 + Ports & Adapters**。

## 1.2 已经成熟、必须保留的能力

### A. 不可变镜头版本

`shots.current_revision_id` + `shot_revisions` 的方向正确。

这意味着：

- 镜头当前状态有明确版本。
- 修改导演意图可以生成 revision。
- 可冻结。
- 后续生成可绑定某个确定 revision。
- 可以审计“哪个版本生成了哪个结果”。

未来新增情绪、表演、转场、声音意图、构图结构等，不应该倒退为直接更新 `shots` 的可变字段。

### B. Media Asset / Media Version

媒体不是“一个文件路径”，而是资产 + 版本。

这一点是后续实现：

- 候选图
- 三视图
- 角色状态
- 首尾帧
- 视频版本
- 重抽
- 后处理
- 超分
- 音频版本

的基础，必须继续复用。

### C. Generation Intent / Variant

现有 `generation_intents` / `generation_variants` 已经能表达：

- variant number
- variant type
- parent variant
- branch reason
- prompt revision
- capability profile version
- parameter set
- seed policy
- input fingerprint
- recipe hash
- status

这就是“重新抽卡 / 分支 / 对比 / 复现”的核心模型。

**结论：未来的“重抽”按钮必须调用这一套，而不是另建表。**

### D. Variant Input Binding

现有 `variant_input_bindings` 能冻结生成时真正引用的媒体版本。

因此未来要区分：

- “角色资产当前主参考图是什么”；
- “当时这个 Variant 实际用了哪个 media_version”。

角色资产更新不可以把历史生成证据一起改掉。

### E. 首尾帧与连续性证据

现有：

- `frame_anchors`
- `shot_transition_constraints`
- stale 机制
- approval reference

已经非常接近专业“Frame Bridge”底层。

未来 UI 要重做成可视化的“上镜尾帧 → 本镜首帧 / 本镜尾帧 → 下镜首帧”，但底层优先映射现有模型。

### F. Job 与自动化

现有：

- durable jobs
- attempts
- progress
- resource lease
- dependencies
- automation workflows
- automation workflow runs
- run tasks
- task → job 关联

因此“生成整集”不缺底层执行系统，缺的是**创作者语义层的编排与可视化**。

### G. Timeline / Review / Delivery

现有 timeline revision、review、selection、delivery 等说明项目已经具备“生产系统”而不是“单次生成器”的骨架。

重构重点应该是把这些能力带到用户当前上下文附近，而不是继续让用户在顶层菜单来回跑。

# 2. 当前架构的核心问题

## 2.1 问题一：`App.tsx` 正在承担 Shell + Router + Query + Orchestrator + 页面拼装

当前 View：

```ts
type View =
  | "overview"
  | "projects"
  | "canvas"
  | "reviews"
  | "jobs"
  | "profiles"
  | "generation"
  | "diagnostics";
```

并自己处理：

```text
view / project / episode / shot / review
```

query parameter 与 `window.history`。

这在功能少时可控，功能变成导演台、资产 Bible、分集运行、模型偏好、音频、时间线后会快速失控。

### 必须改变

`App.tsx` 最终只负责：

1. Provider。
2. Error boundary。
3. Router。
4. AppShell。
5. 全局 toast / modal / event channel。

页面业务不再在 `App.tsx` 条件分支拼装。

---

## 2.2 问题二：页面按“代码模块”组织，不按“用户任务”组织

当前“分集生产”纵向堆叠：

- EpisodeSceneRanges
- StoryboardBatchWorkbench
- CreativeLibrary
- StoryAssetLibrary
- ScriptImport
- AI Draft Review
- Dialogue TTS
- Audio Track
- Subtitle Revision
- Timeline Revision
- Contact Sheet
- Episode Review
- Export
- Delivery
- Readiness
- Configuration Snapshot
- Brand Kit

这种页面对开发者很好理解：每做完一个 Feature 就加一块。

但用户的真实任务是：

> “我正在做第 03 集第 12 镜，现在人物脸不稳定，我想换参考图后重抽这一镜，然后看它和 11 镜尾帧是否接得上。”

用户不应该为了这一件事在四个顶层页面之间跳转。

---

## 2.3 问题三：Application 层大量直接依赖具体 infrastructure

维护性审计已经报告：

- domain boundary 通过；
- concrete infrastructure boundary 未通过；
- application 中大量直接 import `local_drama.infrastructure.database.sqlite`；
- 还有 Comfy、manifest、local_llm 等具体实现泄漏；
- routes 中 workflows / profiles / adapters 也直接接触 infrastructure。

典型：

```py
from local_drama.infrastructure.database.sqlite import Database
```

直接出现在 application service。

### 风险

1. 业务规则和 SQLite SQL 纠缠。
2. 单元测试需要构造真实 DB。
3. Director Desk read model 很容易继续堆 SQL。
4. 更换存储方式非常困难。
5. Runtime / model adapter 边界继续扩散。
6. Agent 为“赶功能”会复制已有风格，越改越粘。

### 目标

不是马上换 ORM，不是马上换数据库。

而是：

> **application 依赖 Port；SQLite 只是 Port 的一个实现。**

原有 SQL 可以先原封不动移动到 repository adapter。

---

## 2.4 问题四：Application service 已经出现巨型领域文件

较大的模块包括：

- `timeline.py` ≈ 1,826 行
- `generation.py` ≈ 1,442 行
- `reviews.py` ≈ 1,250 行
- `projects.py` ≈ 989 行
- `profiles.py` ≈ 824 行
- `dialogue.py` ≈ 814 行
- `project_packages.py` ≈ 754 行
- `automation_workflows.py` ≈ 749 行
- `media.py` ≈ 701 行
- `jobs.py` ≈ 687 行

这不一定等于“代码差”，但说明下一批功能绝不能继续往这些文件加。

### 新增功能规则

从本次重构开始：

- 新 Director Desk 相关代码按 command/query 拆。
- 新 Story Bible 用独立 bounded context。
- 新 Model Capability resolver 独立。
- 新 Episode Production Run 是 facade/orchestrator，不挤进 `automation_workflows.py`。

---

## 2.5 问题五：资产模型只到“单张 canonical 图”

当前 `story_assets` 可以：

- CHARACTER / SCENE / PROP / COSTUME；
- name/code/description；
- 一个 `canonical_media_version_id`；
- extra JSON；
- 与 shot 绑定。

这只能支撑“有一张主参考图”，不能真正支撑：

- 三视图 / 四视图；
- 表情表；
- 全身/近景；
- 角色不同服装；
- 剧情状态（受伤、换装、年龄变化）；
- 不同场景时间/天气/灯光状态；
- 哪一张被锁定；
- 哪些参考适用于哪一集/哪一镜；
- 角色音色与状态协同。

而现有 UI 甚至需要用户手工粘贴 `canonical 媒体版本 ID`，这是典型工程后台交互，必须去掉。

---

## 2.6 问题六：Model/Profile 概念正确，但暴露层级太底

现有 Provider / Model / Workflow / Execution Profile 的可复现性设计值得保留。

问题是创作用户更关心：

- 这个模型能不能角色参考？
- 能不能首尾帧？
- 这张 3090 Ti 大概跑多久？
- 这个镜头需要动作一致，哪个配置更稳？
- 我整个项目默认用 A，只有几个镜头用 B。

而不是：

> “选择 provider_version + model_version + workflow_version + profile_version”。

必须在二者之间新增**能力选择层与偏好继承层**。

# 3. 目标总体架构

## 3.1 仍采用模块化单体

目标：

```text
┌────────────────────────────────────────────────────────────┐
│                         Web App                            │
│ Route Pages → Feature Modules → Query/Command Client       │
└─────────────────────────────┬──────────────────────────────┘
                              │ HTTP + SSE
┌─────────────────────────────▼──────────────────────────────┐
│                        FastAPI API                         │
│ Route Adapter / DTO / Auth(Local) / Error Translation     │
├────────────────────────────────────────────────────────────┤
│                      Application Layer                    │
│ Commands │ Queries │ Orchestration │ Policies │ Ports     │
├────────────────────────────────────────────────────────────┤
│                         Domain                             │
│ Director Intent │ Asset Bible │ Generation │ Review Rules  │
├────────────────────────────────────────────────────────────┤
│                      Infrastructure                        │
│ SQLite Repos │ FS Media │ Comfy │ LLM │ FFmpeg │ Manifest │
└────────────────────────────────────────────────────────────┘
```

**不要拆微服务。**

理由：

- 本地运行；
- 单用户/小团队；
- SQLite；
- GPU runtime 位于本机；
- 拆网络服务增加启动、调试、版本和故障面；
- 当前真正痛点是代码边界与 UI 心智，不是吞吐型服务扩容。

# 33. 资产变更后的 Stale 传播

## 33.1 原则

不能因为资产换图就自动“让旧视频变成新角色”。

### 当前语义变化

```text
StoryAsset reference R1 -> R2
```

历史：

```text
Variant V1 input binding = R1 media_version
```

仍然成立。

### 新状态

系统计算：

```text
V1 uses non-current asset ref → POSSIBLY_STALE
```

对下游：

- 当前 selected variant 提示 stale；
- frame bridge 若依赖 V1 可提示 stale；
- timeline item 若引用 V1 不自动替换；
- Episode Run 若策略要求 current assets，可安排 rebuild。

## 33.2 传播实现

P0 可以 query-time 计算 + 少量 stale flag。

不要第一版就造复杂 event sourcing。

P1 再引入 domain event：

```text
StoryAssetReferenceChanged
SelectionChanged
ShotRevisionChanged
GenerationVariantSelected
FrameAnchorChanged
```

并触发 read model invalidation / stale marking。

# 71. 数据迁移回滚原则

SQLite schema migration 通常不能靠“直接 downgrade 后假装没发生”。

每个 migration 前：

- 本地 DB backup；
- migration dry-run test；
- backfill count；
- invariant verify。

新表优先 additive。

0042～0046 都设计为 additive，就是为了降低风险。

### A.2 部分实现，只补缺口

## B. Phase 0：四个必须先合入的修复

### B.1 P0-01 Episode Plan cache contract collision

根因不是 `find` 少了 guard，而是同一 cache key 的类型被破坏：

## E. 真正的“一键整集”Production DAG

### E.1 图定义

```text
SOURCE_COMMIT
  -> STORY_BREAKDOWN [human gate]
  -> ASSET_PROPOSALS [human gate]
  -> IDENTITY_PACKS [human gate]
  -> EPISODE_PLAN [human gate]
  -> SHOT_KEYFRAMES
  -> VIDEO_GENERATION
  -> SHOT_QC [exceptions/human gate]
  -> AUDIO_TTS
  -> TIMELINE_FREEZE [human gate]
  -> EPISODE_RENDER
  -> RENDER_REVIEW [human gate]
  -> DELIVERY_PACKAGE
```

每个 ProductionNode 保存：node type/status、input snapshot hash、dependency node IDs、resolved model snapshot、recipe/QC version、Job IDs、output refs、attempt、blocker、human decision、stale reason、started/finished。状态限定 `NOT_READY / READY / QUEUED / RUNNING / WAITING_HUMAN / SUCCEEDED / FAILED / STALE / CANCELLED / SKIPPED`。

### E.2 编排语义

- DAG service 只规划和提交现有 Job；worker 不扫描 UI 状态猜下一步。
- `start/resume/retry-failed/cancel` 都有 idempotency key；重复点击返回同一次 run/action。
- 上游版本变化只将依赖 node 标 stale；已选/已批媒体不删除。
- human gate 未批准时不能由 AUTO 规则越过；可配置“低风险批量批准”，但要保存规则版本和例外。
- 节点失败不阻塞无依赖分支；整集状态是投影，不是又一列手工写状态。
- UI 的 stage 进度来自真实 node/job 计数；未实现的 handler 显示 `NOT_IMPLEMENTED_REQUIRES_MANUAL`，不伪装运行。

### E.3 首批必须实现的前半段 handlers

1. `RequestStoryBreakdownAction`：解析 Profile、创建 LLM Job、持久 draft，等待人工 apply。
2. `ProposeAssetsAction`：从已应用 breakdown 创建 Proposal，不创建虚假 approved asset。
3. `BuildIdentityPackAction`：引用现有 media/reference，缺槽位时创建 multiview Job，等待人工批准。
4. `PlanEpisodeAction`：生成 plan/replan draft，等待 diff/apply。
5. `GenerateKeyframesAction`：按已批准 Intent + Identity Pack + Frame Bridge 创建 Variant Job。

只有这五个与现有后半链路打通后，产品才可对外写“从剧本一键成片”。在此之前文案应为“从已就绪镜头继续批量生产”。

## G. Worker、存储与本地可靠性

### G.1 Local Supervisor

新增 `WorkerSession` 投影：session id、pid、host、started/heartbeat、state、capabilities、GPU/VRAM、active jobs、version。启动器必须选择一种可维护机制（随桌面应用进程托管或 OS service），并保证：

- API 在线、worker offline、worker idle、worker busy 是四种不同状态。
- 自动重启有退避和上限；异常循环进入 degraded 并给诊断链接。
- lease/heartbeat 和 orphan recovery 沿用现有 Job 语义。
- Shell 只有在 supervisor 确认活跃时才显示“关闭浏览器不会中断”。
- API/worker 版本不兼容时拒绝接单。

### G.2 文件—DB 一致性

当前 copy 与 DB commit 之间需要补偿日志。采用 staged ingest：

1. 在项目限定 staging 目录创建 `StorageOperation(PREPARED)`。
2. 流式复制并流式 hash；拒绝 symlink/path traversal/超限文件。
3. fsync/校验后写 MediaVersion 与 operation `DB_COMMITTED`。
4. 原子 rename 到 content-addressed final path，标 `FINALIZED`。
5. Reconciler 处理 `PREPARED`、`DB_COMMITTED`、孤儿 final、hash mismatch；不静默删除，先 quarantine/report。

禁止对大媒体 `read_bytes()` 计算 hash；测试设内存预算并 fault-inject copy 后 DB fail、commit 后 finalize crash、重复操作、磁盘满。

## H. Local Edition 与 Connected Edition

当前安全基线是 LOCAL_ONLY。用户希望选择豆包、MiniMax 等云模型时，必须先批准 Connected Edition ADR，而不是把 API Key 塞进 Profile JSON。

必须新增：

- `Provider` / `ProviderCapability` / `CredentialRef`（只保存 OS credential vault reference）。
- 明确 egress consent：上传内容类型、供应商、地区、保留策略、费用上限、取消语义。
- provider adapter 只通过 port 接收短生命周期 credential；secret 不进 SQLite、日志、导出包、URL、localStorage。
- capability matrix 与健康检查；rate limit/cost/risk；请求/响应审计只存摘要和 hash。
- project/asset 级“禁止外发”策略，默认 fail closed；本地 fallback 也必须显式且能力兼容。
- provider contract test、sandbox E2E、数据删除/撤回流程。

UI 里“本地 / 云端”是一级标签；选择云模型前显示哪些素材将外发。无 ADR 和 vault 之前，文档只允许设计该能力，禁止开发 Agent 直接接生产 Key。

## L. 架构完成定义

- 所有 V2 route 在空项目、真实项目、大项目下均有 typed loading/empty/error，绝不进入默认开发错误页。
- exact query key 只有一种 return type；无新增 raw query key；generated client 与 OpenAPI 无 diff。
- URL、当前选中镜头、preflight、POST 与 Job snapshot 一致。
- 同一 capability 在设置、Director、Manual Generation、Run、worker 解析到同一发布版本与 fingerprint。
- 每个 Variant/Job 可追溯 source/intent/asset pack/frame/model/workflow/seed/recipe/QC/output。
- selected、adopted、approved、delivered 不合并；机器证据不自动成为人工批准。
- worker 崩溃和浏览器关闭后，已接管 Job 可恢复；没有 worker 时 UI 诚实阻塞。
- 文件/DB fault injection 后 reconciler 能收敛到 0 unresolved 或明确 quarantine。
- 默认本地 fail closed；云外发有 vault、consent、审计、预算和取消。
- 架构重构没有创建第二套媒体、候选、时间线、Job 或 Run 真值。

# 92. 最终架构判断

LocalDramaStudio 当前最值得珍惜的是底层“可追溯的本地生产事实模型”。竞品最值得学习的是把复杂能力隐藏在**清楚的创作者工作台**里。

因此架构方向不是：

> “为了做得像竞品，把现有底层全部推倒。”

也不是：

> “已有功能这么多，只换一套 CSS。”

而是：

> **保留证据链，重构边界；保留执行能力，重做用户心智；把工程 Profile 变成能力，把散落 Panel 变成导演台，把自动化 Workflow 变成整集生产 Run，把单张 canonical 资产升级成真正的角色/场景 Bible。**

这才是可以继续扩展几年而不是继续堆页面的架构。

### 2.1 本批次发现并修复的两个真实缺陷

这两个缺陷都是先在真实路径上暴露、再定位到根因，然后修复并加了回归证据：

1. **显式事务内的二次提交**：`Database` 使用 `isolation_level=None`，`transaction()` 已显式
   `BEGIN IMMEDIATE`；此时再调用 `connection.commit()` 会**结束**该显式事务，后续语句抛
   `sqlite3.OperationalError: cannot commit - no transaction is active`。
   修复：`infrastructure/database/sqlite.py::transaction` 只在仍处于事务中时提交，并让
   `application/explainers/narration.py` 的内部提交成为有文档说明的空操作。
2. **`create_script_revision` 的返回形状假设**：处理器曾按 `created["id"]` 取 revision，
   而服务返回的是 `{"script_revision", "segments", "chapters"}`，会在真实运行时报错。
   修复：按真实契约取 `created["script_revision"]`，并由 `NARRATION_WRITE` 的测试覆盖。

### 8.2 本批次修掉的真实缺陷

| 缺陷 | 后果（实测） | 修复 |
|---|---|---|
| **字幕切分按字符数硬切，不看标点** | 交付版出现 `…监狱的` / `铁网。`、`直接硬` / `闯必死无疑`、`利用5` / `0件偷来的雨衣…` 这类读不通的 cue | `_split_cue_chunks` 改为**子句优先**：先句子标点，再子句标点（，、：），再词边界；不切断 ASCII 数字/字母串；不留短于 6 字的碎片；整窗都是一个 token 时按窗口边缘切 |
| **对齐时钟的采样率错位 3 倍** | 对齐器是 16 kHz 采样位置，修订却声明 take 的 48 kHz；13 个字拿到 773 ms、22 个字拿到 5.97 s，`exceeds_limit_count` 一度到 23（最高 21 字/秒） | 新增 `rescale_word_timings`：对齐位置按**对齐器自身采样率**换算到 take 采样率；单段对齐与批量对齐两条路径都上报 `aligner_sample_rate_hz`；转换比例记入 `asr_review_json.alignment_clock` |
| **不可信的对齐时钟被当成时钟用** | 旧库里"只覆盖片段三分之一、隐含 19 字/秒"的地图照用不误 | 新增 `_alignment_clock_verdict`：覆盖率 < 0.5 或每字时长超出 60–500 ms 即判定不可信，整段退回按字数比例分配，并把原因写进 `cue_clock_rejections` 与 `alignment_facts.clock` |
| **对齐修订无法重测** | 对齐修订是追加式、阶段只处理"还没有修订"的 take，坏时钟永远修不掉 | 新增 `POST /api/v2/explainer-editions/{edition_id}/narration:align`（每个已采用 take 一个真实 `NARRATION_ALIGN` 任务）与旁白页「重新对齐旁白」按钮 |
| **单次 `loudnorm` 动态归一化落不到目标** | 交付文件 -18.0 LUFS，比声明区间低 1 LU | 混音后增加**测量 + 线性校正**两遍（`build_loudness_measure_command` / `build_loudness_normalise_command`、`FfmpegRunner.normalise_loudness`），烧录版与干净版都走同一条校正 |
| **技术质检层从不测音频** | `AUDIO_LOUDNESS_NOT_MEASURED` / `AUDIO_TRUE_PEAK_NOT_MEASURED`，响度区间实际上没人验 | 解码验证器新增 `ebur128=peak=true` + `silencedetect` 实测，映射到技术层输入（`loudness_lufs` / `peak_dbtp` / `audio_gaps_ms`） |
| **成片级质检被深度层一击打死** | `COMPOSITION_QC` 抛 `SCHEMA_INVALID frame_range`，技术层与字幕层已测到的报告全部丢弃 | 深度层只覆盖单镜头：成片级直接记为 `DEPTH_LAYER_SCOPE_IS_ONE_SHOT` 未运行；每层输入/报告各自容错（`NOT_RUN`/`DECODE_TOOL_UNAVAILABLE`/`CAPABILITY_UNAVAILABLE` 只让该层未运行，真实故障仍然抛出） |
| **质检层没有独立命令** | 逐页驱动的成片，交付包里的 `qc_report.json` 只能是 `{"status":"NOT_RUN"}` | 新增 `POST /api/v2/explainer-editions/{edition_id}/qc:run`（可指定 `render_id`）+ 审核页「运行技术质检」按钮 |
| **质检阶段把整段工作放在一个事务里** | 长时间运行会让 worker 自己的租约心跳拿不到写锁 | 每一层、每个读取端口各自一个短事务（与渲染阶段同一条规则） |
| **租约续期遇到一次"database is locked"就放弃** | 同类竞争让长任务被判 `WORKER_LEASE_EXPIRED`（本次成片质检连续三次） | 心跳对**数据库锁竞争**做有限次退避重试（3 秒 ×12），其它错误（租约丢失、取消）仍然立即停止；`EXPLAINER_TASK` 初次租约 60 → 120 秒 |
| **多模态批次一失败就整层 NOT_RUN** | 13 批里有 12 批真实读到帧，却因为一批失败把整层降级为"零覆盖" | 逐批容错：失败的批该帧逐帧记为 `SEMANTIC_QC_UNCHECKED`，其余批保留真实覆盖；**全部**批次失败才按原样抛错（层确实没跑） |
| **提供者错误只有异常类名** | 只能看到"多模态调用失败"，无法区分模型服务未起、请求被拒、返回不合 schema | 错误串携带 message 与结构化 details（`LOCAL_LLM_LOOPBACK_UNAVAILABLE / status_code 500` 等），并进入报告与 `unverified_checks` |
| **交付包的 `qc_report.json` 只装"最后写的那一层"** | 语义层 `NOT_RUN` 的报告会盖住同一渲染上 `PASS` 的技术层报告，包内看不出"到底验了什么" | 包内报告改为：最新一份全文 + `layer_reports`（每层 detector/status/时间）+ `aggregate_status`（取最严结论）；`qc_reports_for_subject` 作为唯一取数口 |

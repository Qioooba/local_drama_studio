# LocalDramaStudio 端到端 UI 自动化测试设计文档（V1）

> 文档定位：把「从配置文件到最终成片」的整条创作者流水线，转成**可以在页面上一步步模拟真人点击/输入、可由本机运行并可用视觉模型复核**的测试设计与执行文档。
> 适用对象：测试负责 Agent（你——deepseek-v4-flash-vision-exp）、执行 Agent、人工审核者、发布负责人。
> 目标运行方式：前端 `http://127.0.0.1:5173`，后端 `http://127.0.0.1:3210`，ComfyUI `http://127.0.0.1:8188`（可各自换端口）。
> 覆盖范围：**新项目从零 → 模型/Provider 配置 → 导入长文 → AI 拆解生成剧本 → 分集策划 → 资产圣经 → 导演台（导演意图 / 首尾帧 / 候选重抽）→ 生成（关键帧 / 代理 / 正式）→ 整集生产 → 本集审核 → 声音 → 时间线 → 交付 → 任务/诊断/项目维护** 的**每一条功能点 + 每一条真实点击路径**。
> 配套：`LocalDramaStudio_Blueprint_v2/`、`docs/xinjihua/01-03`、`F:\AI_Projects\h3\家庭剧全自动生成流水线实施路线图.md`、`F:\AI_Projects\h3\model_manifest.json`。
> 逐页精确交互（每个按钮/字段/端点）的“Feature Sheet”位于 `docs/testing/feature_sheets/`（`FEATURE_SHEET_project_story.md`、`FEATURE_SHEET_EPISODE_PLAN_DIRECTOR_DESK.md`、`FEATURE_SHEET_AssetBible_QC_Recipes_Settings.md`、`FEATURE_SHEET_Review_Audio_Timeline_Delivery.md`；生成/媒体/模型详见 §7/§2.3）。所有端点均已对照 `apps/web/src/generated/api.ts` 与后端 `routes/` 核实。

## 0. 设计说明（先读这段）

### 0.1 这张文档和「旧的迁移验收手册」的区别

- `03_实施迁移测试验收手册.md` 是**迁移/重构**视角，关心“这次改造是否保住了旧证据、PR 怎么分”。它适合开发、不适合“把整条创作流程点一遍”。

### 0.3 一次完整真人操作对应的「流水线语义」

`model_manifest.json`/`series_config.yaml` 与 `本地AI短剧工厂_Web系统详细设计_v1.1.md §28.2` 给出的权威流水线，也是本文档的阶段顺序：

```
故事/母本 → 分集与剧本 → 资产抽取 → 人物/场景/道具母版审核
   → 导演分镜与关键词 → 提示词冻结 → 关键帧候选 →【图片人工审核】
   → 代理视频多 take 抽卡 →【选择代理 winner】 → 正式分辨率生成 →【正式视频审核】
   → 对白/TTS/字幕 → 音效/环境/音乐 → 时间线/混音/字幕 → 整集渲染 →【整集人工审核】
   → 交付包与 SHA-256 校验
```

域模型：**季(season) → 场(scene) → 发布切片(cut) → 镜头(shot)**；`series_config.yaml` 即这一项目的“母本规格”：

```yaml
format:  aspect_ratio: 9:16, fps: 24, season_duration_sec: 7200, release_cut_count: 60,
        target_cut_duration_sec: 120, cut_duration_tolerance_sec: 15
content: genre: 当代乡村家庭伦理, era: 当代, region: 虚构北方丘陵小镇/柳湾村,
        audience_age: 40-70, language: 普通话, visual_style: 暖色现实主义低饱和写实,
        tone: 现实冲突、温情回收、克制希望, content_rating: 大众
continuity: core_character_min_cut_appearances: 12, recurring_character_min_cut_appearances: 4,
        require_asset_version_lock: true, require_start_end_state: true
production: proxy_resolution: 480p_or_540p, final_resolution: 768p_or_2K,
        proxy_candidates_per_shot: 3, max_proxy_retries: 2
```

> 这是“项目开始时可参考/导入的素材基线”；界面上**不会自动套成默认**，必须由你在页面显式配置后才能生产（蓝图多次强调“禁止暗选 H3 / 分辨率 / 交付规格”）。

## 1. 测试策略总览

### 1.1 执行方式：三种测试类型都要覆盖

| 类型 | 谁执行 | 本文档给什么 |
|---|---|---|
| **E2E 页面链路（主）** | 你（视觉模型）+ 驱动脚本 | 每阶段“用户点击/输入动作表” + 触发 API + 预期结果 + 截图证据 |

| **边界/错误/权限** | 自动化 + 人工 | §7 的边界用例（空态、错误、SSE 断线、双击幂等、只读权限、版本冲突） |

### 1.2 通过门槛（每个阶段都要打勾）

1. 每个页面至少过一遍 `loading / empty / normal / error / large-data` 五种状态。
2. 每个“生成/提交”按钮在表单完整时可用、双击只产生一个 Job / 一个 Batch。
3. 状态语义与文案分离：`已选择`≠`已批准`；代理 winner≠正式批准。
4. 任何“本地 Profile 不可用”只阻塞绑定该能力的节点，不阻塞全页。
5. 每个生成产物都要有可追溯输入快照（prompt / 参考图 hash / seed / Profile 版本 / folder）。「无输入快照的产物」记为 FAIL。

### 1.3 记录产物（每个用例结束都要有）

- 截图（整页 + 交互后状态）。
- 网络请求（触发端点 + 请求体），用于核对“点了哪个按钮 → 打哪个 API”。
- 文本 / JSON（生成的剧本、拆解草稿、镜头表、prompt、QC 报告）。
- 媒体文件（关键帧、代理 take、正式视频、首尾帧、成片、交付包）。
- 结果落点：`docs/evidence/<run_id>/` 或 `temp/……`，并且不覆盖历史。

### 1.4 缺陷记录模板


### 2.4 页面能力：新增 OpenAI 兼容 Provider（DeepSeek）——本期必做的改造

> **结论（已确认）**：走「加 OpenAI 兼容 Provider」。当前代码只支持 loopback Ollama，需要做一次小改造。下列为**测试应先确认已实现**的功能契约，也是“配置 DeepSeek”在页面上的落点。

- Provider 通用字段（设计文档 §29.2）：名称、类型、**本地/云**、**base URL**、认证方式、能力、模型映射、默认超时、轮询周期、最大并发、rate limit、重试、代理、估价规则、数据区域、是否允许上传人物/音频/剧本、最后健康检查、许可备注。
- **OpenAI 兼容远程 provider 用 `https://api.deepseek.com`**（OpenAI SDK 兼容，`POST /v1/chat/completions`；也可用 `https://api.deepseek.com/v1`）。认证 `Authorization: Bearer <api_key>`。
- 模型：`deepseek-v4-flash-vision-exp`（多模态 vision + 文本，既能写小说/剧本，也能看图/视频评审）。
- API Key：`<通过环境变量或凭据引用配置>`。**只存引用，不落明文 SQLite/YAML/日志**；前端只显示 `configured: true` 与末 4 位；日志对 `Authorization`/`Cookie`/query secret 脱敏（设计文档 §29.2）。
- 能力映射（业务 profile → provider/model）：例如「剧本拆解 `LLM_STORY_PARSE`」可映射到 DeepSeek；「视觉评审 `QC_VISUAL/QC_FACE/QC_IDENTITY`」亦可映射到该多模态模型。
- **“测试连接”四级**：网络/进程可达 → 认证成功 → 能力/模型可用 → 最小样例成功。只有第 4 级能用于 production profile（设计文档 §29.4）。

> 说明：本期改造需要新增一个 `OpenAICompatProvider` adapter（现状只有 `ComfyUI`、`loopback Ollama` 等），并把 `LocalLLMClient` 的“仅 loopback + 仅 Ollama 协议”守卫放开为“允许已配置的开放地址 + OpenAI 消息协议”。这是“能从第 1 步把 DeepSeek 配进项目”的硬前提；**在实现前，相关测试步骤记为“待实现/阻塞”，不伪造通过**。

## 4. 阶段 C：长文导入 + AI 拆解（生成“小说/剧本”）

> **必须澄清的设计事实**：本项目**没有“从空白写小说/剧本”的按钮**。“生成小说/剧本”的真实动作 = **导入一部已有小说/剧本/长文（TXT/MD/DOCX）→ 用本地/DeepSeek LLM 做“剧本拆解”**，产出结构化场次/镜头/对白**草稿**，再由你**显式应用到某个分集**。因此“生成小说”理解为“导入源文本 + AI 拆解”，DeepSeek 在此处承担拆解（和后续可视化评审）。

页面：`/projects/<id>/story`，标题「从长文原稿到可审核的生产事实」。四个阶段（`#story-bible / #story-import / #story-review / #story-assets`）。

## 10. 视觉/媒体自动化评审协议（由你 deepseek-v4-flash-vision-exp 执行）

> 你具备图像 + 视频理解。每个“截图/媒体”产物按下述清单评审，输出结构化评审 JSON 供人工复核。

### 10.1 截图评审（UI 正确性）
- 关键控件是否可见、可点击、无遮挡/溢出（横向溢出是旧风险）。
- 状态 pill 文案与颜色是否符合语义（§1.2）。
- 是否有重复/错位/未翻译文案、控制台报错（`console_errors`）。
- 空态/错误态文案是否给出主行动。

### 10.2 图像/关键帧评审（一致性）
- 角色五官/发型/服装/年龄一致性；场景建筑/季节/天气/时间一致。
- 无明显手指/肢体/道具/文字/脸部/背景变形。
- 网格、摩尔纹、整帧噪声（H3 已知坏件问题，需在首中尾帧检查）。

### 10.3 视频评审（首帧/中帧/尾帧 + 人脸局部）
- 抽首/中/尾帧，比对人物身份、朝向、服装、场景、道具。
- 人脸局部放大图比对（同一角色是否漂移）。
- 动作连续性：`continuity_mode: first_last_frame` 的镜头必须检查动作/道具衔接（已知为部分失败项）。
- 代理通过 ≠ 高清通过；高清必须二次 QC。

### 10.4 音频/成片评审
- 对白可听清、音画同步；字幕与对白逐字匹配、字号/描边/安全区适配中老年。
- 响度、削波；无黑帧/水印/现代错误元素。

评审 JSON 模板：`{ media, kind, reviewer="deepseek-v4-flash-vision-exp", model_capability:"vision", frame_checks:{first,middle,last,face}, pass_boolean, risks[], evidence_ref }`。

## 12. 自动化驱动与执行计划（怎么“在页面自动点击”）

> 原则：所有页面动作都写成了“用户动作 → 触发 API → 预期”的三元组。执行时用 **Playwright（对应仓库已有 `scripts/crawl_ui_exhaustive.mjs`、`apps/web/uat/*.mjs`、`scripts/full_control_interactive_runner.mjs`）** 驱动浏览器点击，并在每次交互后**截图 + 记录网络请求**，随后把截图/媒体交给本视觉模型评审。

### 12.1 驱动脚本骨架（按阶段串起来）

```mermaid
flowchart LR
  A["阶段A 环境/配置"] --> B["阶段B 新建项目"]
  B --> C["阶段C 导入长文+AI拆解"]
  C --> D["阶段D 分集策划"]
  D --> E["阶段E 导演台(意图/首尾帧/重抽)"]
  E --> F["阶段F 生成(关键帧/代理/正式)"]
  F --> G["阶段G 资产圣经"]
  G --> H["阶段H 审核(图片/代理/正式)"]
  H --> I["阶段I 声音/字幕"]
  I --> J["阶段J 时间线"]
  J --> K["阶段K 整集生产运行"]
  K --> L["阶段L 整集审核"]
  L --> M["阶段M 交付"]
  M --> N["系统区: 任务/诊断/维护/画布"]
```

### 12.2 每阶段固定动作序列（Playwright）
1. `page.goto(<route>)` → 等待 `skeleton/数据加载`（`waitForSelector` 或 networkidle）。
2. **截图 1**：整页（记录 `Loading/Empty/Normal` 态）。
3. 按“用户动作表”做 `click/fill/select`，每个动作后**截图 2 + 捕获 `request/response`**。
4. 断言预期（文本出现 / 状态 pill 文案 / 计数一致 / 按钮 disabled）。
5. 触发生成的动作，点击后**不等待全完成**，改为轮询 `GET /jobs` / SSE，直到终态。
6. 记录产物路径（文本/图片/视频/JSON）到本次 run 的 evidence 目录。
7. 最后一步：`page.screenshot('fullPage')` + 调视觉模型评审（§10）。

### 12.3 证据与回滚
- 每个 `run_id` 一个目录；失败时保留全部已生成产物（不覆盖历史）。
- 任何生成动作都先记录“输入快照”（prompt/seed/参考图 hash/Profile 版本/计划哈希），否则该产物记 FAIL。
- 回滚：项目/分集/镜头的**历史 revision 不可覆盖**；改坏只能派生新 revision，不能改历史。

### 12.4 分阶段执行的“暂停点”（人工审核点）
`关键帧 →【人工审图】 → 代理→【人工选 winner】 → 正式→【人工审核】 → 整集→【人工审核】 → 交付`。这些是硬闸门，自动化**不能**越过，只能“生成候选并提示人类/我来审核”。检测到“把一个生成动作自动批准成成品”即判 FAIL。

### 12.5 工作量拆分（可并行跑的分区）
- 分区 1（配置/项目/长文）：阶段 A–C。
- 分区 2（策划/导演/生成/资产）：阶段 D–G，最重。
- 分区 3（审核/声音/时间线/交付/系统）：阶段 H–N。
每个分区一个 Playwright 配置文件，输出独立 evidence 目录。

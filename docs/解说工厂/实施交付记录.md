依据：《解说工厂：体验、功能与代码改造实施规范》（下称《规范》）与同目录 `prompts/`。
实施对象：`F:\AI_Projects\h3\local_drama_studio`。

本文件记录**已实施内容、接口与数据变更、验证证据、明确未完成/未验证项**。任何未实际执行的项目都按《规范》§F6 标 `NOT_RUN` / `BLOCKED`，不以 HTTP 状态、任务行数或页面存在冒充完成。

> **本轮（2026-09-25）最关键的三个结论**
> 1. **文生图产品闭环从“计划能过、提交必败”推进到真实出图**，并用同一条链路重跑了 10 种解说风格、逐张做了本机视觉判读与页面点击验证（§3.7、§3.8）。
> 2. **成片真机验收发现并修复了三个会直接毁掉交付物的缺陷**：成片被渲染成 854×480（管线自己生成的是 1080p 卡面）、**82.3% 的成片是数字静音**（52 条旁白只有 9 条被混进去）、真峰值超出产品自述上限。修复后同一作品重渲染：**1920×1080 / −17.0 LUFS / LRA 8.6 / −1.6 dBTP / 静音 0.5%（一段 1.95 s，来源是旁白自带的句间停顿）**，并有真实 FFmpeg 回归用例（§3.9、§0）。
> 3. **超分（图像/视频）在本机 NOT_RUN**，凭据来自产品自己的拒绝（`UPSCALE_NCNN_EXECUTABLE_NOT_FOUND`、`UPSCALE_PROFILE_NOT_CONFIGURED`）与磁盘实测（没有 ncnn 可执行文件，`upscale_models` 里只有 0 字节占位文件）（§3.10）。
>
> 仍未完成：图生视频 V2 接线（§4 第 17 项）、14 篇文体审计的第 09–14 篇（§3.11）、以及抽取阶段两类“模型错误即整阶段失败”的处理缺口（§4 第 25、26 项）。这些都如实记录，未伪称可用。

**真实模型下发现并已修复的阻塞缺陷**（都是 A 层假客户端永远测不出来的）：

1. **JSON Schema 直传导致所有文本阶段 HTTP 400（最严重）**：客户端把 Pydantic 生成的完整 schema 放进 Ollama 的 `format`，而 llama.cpp 的 GBNF 转换器拒绝其中部分取值——实测**任何长度约束等于 2000 的值**（`maxLength`/`minLength`/`maxItems`）都会让请求以 `Failed to initialize samplers: failed to parse grammar` 400 失败（1999 与 2001 正常）。七个契约**每一个**都带 `maxLength: 2000`，因此真实环境下 `FACT_EXTRACT` 等阶段 100% 失败。修复：新增 `grammar_safe_schema()`，在**发送前**确定性投影掉只做校验、不塑形的关键字（长度/pattern/format/数值边界），结构关键字（type/properties/required/items/enum/anyOf/additionalProperties）保留；服务端仍用完整契约校验。这正是 `prompts/README.md` 第 29 行允许的做法。用例：`test_local_llm_structured_output.py`。
2. **`events[].title` 被 schema 展开吃掉（第二个阻塞缺陷）**：`expand_json_schema()` 用 `_UNSUPPORTED_KEYWORDS` 过滤注解关键字，但 `properties` 映射的键是**字段名**——于是数据模型里名为 `title` 的字段被删掉，而 `required` 仍列着它。发给模型的 schema 出现“要求一个没声明的字段”，grammar 无法强制、模型就不写，Pydantic 再拒绝，唯一一次格式修复返回同样的形状，阶段在约 870 秒后以 `SCHEMA_INVALID` 失败。**实证**：第 01 篇科普（0 个事件）通过，第 02 篇历史（4 个事件）三阶段全失败，错误正是 `events.0..3.title Field required`。修复：新增 `_NAME_MAP_KEYWORDS`，`properties`/`patternProperties`/`$defs` 下的键名不再当注解过滤。用例：`test_explainer_schema_expansion.py`（含不变量“`required` 里的每个名字都必须在 `properties` 中声明”，七个契约全覆盖）。
3. **口播稿没有使用设计态提示词**：`NARRATION_WRITE` 实际发送的是自写的短 system（`PlannerPrompts.script_system`，4 句）+ 自写 user 提示词 + 旧 `SEGMENT_SCHEMA`，`script-draft.v2` 的 `SCRIPT_DRAFT_SYSTEM/USER` 与契约校验代码（`_plan_script_from_draft`）在生产路径上不可达——真实模型的产出就是把来源句逐条抄成 12 段（12 段全 `FACT`、1:1 对应 claim，无开头提问、无过渡、无结尾回应，403 字符等于原文主要句子）。修复：`_plan_script_contract_first()` 改为**先按设计态提示词与 `script-draft.v2` 契约出稿**，契约不通过才回退旧路径，并在回执里写清 `contract_used`/`v2_fallback_reason`。
4. **分镜提示词缺少片段策略，真实模型给静态画面选了 I2V**：`EXPLAINER_STORYBOARD` 的提示词从未带上用户在第 2 步/创建页选择的 `visual_strategy`，也缺少“推镜不是人物动作 / 按策略选 render_type / 首帧与单一动作 / 提示词语言”这些设计态规则，结果 B001（“静谧场景”，must_be_motion=false）被标成 `render_type=I2V`，且 `prompt_intent` 变成英文。修复：`_visual_strategy_hint()` 把策略与一句话规则注入 user 提示词，并按 `STORYBOARD_SYSTEM` 补齐 system 规则（一处一焦点、推镜≠人物动作、must_be_motion 保留、连续性、首帧/单一动作、不得写可读文字）。
5. **内容提取的实体类型与重要度没有判据**：`CONTENT_EXTRACT_SYSTEM` 是设计文档的逐字实现，但设计文档没有给出 `entity_type` 七选一的判据，也没有要求填 `entity_indexes` 或区分 `importance`。真实模型因此把 甲藻/水母/虾/鱿鱼/鱼类/海萤/共生细菌 判成 `ORGANIZATION`（同一篇重跑又变成 `GROUP`，温度 0.2 下不稳定），把全部 10 条 claim 标成 `CORE`，并且所有 claim 的 `entity_indexes` 都是空数组——后果是第 2 步“需要固定外观”的对象数为 0（自然/生物类题材没有参考图主体），且“核心事实”失去区分度（任何一处冲突都会升级为核心冲突）。修复：在**不删除任何设计态规则**的前提下追加判据（`GROUP` 给生物类群/物种，`LOCATION` 给地点场所即使只出现一次，`ORGANIZATION` 只给人类组织，`CONCEPT` 兜底；claim 谈到实体就必须给索引；CORE 通常不超过三分之一）。用例：`test_explainer_prompt_fidelity.py` 断言“设计文档的每一行规则都必须仍在模板里”。
6. **长度补写循环空转**：真实模型对“再写长一点但不许新增事实”连续三次返回**完全相同**的 403 字符，三个补写调用白花约 180 秒，回执里如实记了 3 次失败尝试。修复：输出没有变长即停止重问并记 `stopped_on_no_progress`；仍保留“有进展就继续”的行为。用例：`test_legacy_expansion_prompt_forbids_inventing_facts` 与 `test_the_length_repair_keeps_asking_while_the_model_makes_progress`。
7. **提示词保真度现在是可测的**：新增 `test_explainer_prompt_fidelity.py` 逐行比对 `prompts/*.prompt.md` 与 `PROMPT_TEMPLATES_V2`，任何一条设计规则被删掉都会失败（允许追加澄清句）。

**真实模型的其它观察（未改行为，如实记录）**：

- 单篇 3 阶段的真实耗时约 12–15 分钟（`FACT_EXTRACT` 270 s、`NARRATION_WRITE` 270 s、`EXPLAINER_STORYBOARD` 220 s），与 `temperature=0.2` 带来的多次重试有关；`num_ctx` 请求 49 152，24 GB 显卡上必须启用 KV 量化与 flash attention 才能 100% 留在 GPU，否则会退化为 CPU/GPU 混合（实测 8 tok/s → 20+ tok/s）。

**本轮修掉的 6 个真实缺陷（每一个都是“上一个是下一个的前置”）**

1. **执行预检哈希在计划与提交之间必然不同（`MP_EXECUTION_RESOLUTION_STALE`）**：提交端把**已解析出的** Profile id 当作 RUN 级显式 Profile 回传，于是预检的 `assignment_chain` 从 SYSTEM 解析变成 `EXPLICIT_RUN_PROFILE`，而 `assignment_chain` 参与哈希 → 同一个 Profile、同一份语义输入也算出两个哈希。修复：`ExplainerVisualPlan` 新增 `requested_execution_profile_version_id`（客户端**请求**的 Profile，而不是解析结果），提交端原样重放。（`scripts/diag_explainer_submit_stale.py` 是这次的定位工具，它会打印每个预检请求与哈希的逐字段差异。）
2. **提交路由把整条命令包在写事务里 → SQLite 单写者自锁**：`_command()` 先 `BEGIN IMMEDIATE`，被调用的提交服务再在自己的连接上 `BEGIN IMMEDIATE`，等待 10 s 忙超时后 `database is locked` → HTTP 500。修复：新增 `_command_owning_service()`（只提供读连接，写事务由服务自己拥有），并用于三个会自己开事务的命令路由（画面段生成、实体参考生成、收集阶段续跑）；其余路由继续用 `_command()`。
3. **残留的托管 llama-server 让所有 ComfyUI 任务在 `prepare()` 就失败**：`ManagedLlamaCppGpuLifecycleAdapter.evict()` 在“有 PID 记录但本机已不再配置 llama.cpp 可执行文件”时抛 `LLAMA_SERVER_BIN_MISSING`，把整次运行时切换判死（实测每个 Comfy 任务都在 7 s 内以该错误结束，根本没开始出图）。修复：新增 `LlamaServerManager.stop_recorded_process()`——**所有权由本机 PID 文件证明，而不是由当前配置证明**，配置缺失时按 PID 驱逐；其它启动失败仍然抛出。
4. **目标运行时自己缓存的权重让显存门永远不满足（`GPU_VRAM_NOT_RELEASED`）**：`prepare()` 只驱逐“其它”运行时，而门限看的是**设备级**空闲显存；上一次失败任务刻意保留的权重（失败时不做 cleanup）与“外部进程占用”无法区分，于是每次切换等满 30 s 后失败。修复：`prepare()` 在记录驻留与目标不一致时先对**目标适配器**调用 `release_cached_state()`（Comfy=卸载缓存模型、Ollama=unload；服务不可达时视为无占用，队列非空仍拒绝），再判门限。
5. **工作流要求 `SEED` 语义输入，而产品把 seed 只放在参数覆盖里**：已发布图像工作流的 `input_slots` 把 `PROMPT`/`SEED` 标为 required，worker 因此以 `MP_COMFY_EXECUTION_INPUT_INVALID(missing=['SEED'])` 拒绝执行；即使能过，同一批多个候选也会全部渲染工作流自带的种子，**“多次抽卡”实际是同一张图**。修复：`_semantic_inputs()` 携带该候选自己的 `SEED`，计划为**每个候选**冻结一份语义输入并各算一次预检哈希（`semantic_inputs_by_seed`），提交原样重放。
6. **空的可选槽位被当成非法标量**：没有风格否定词时 `NEGATIVE_PROMPT=""` 被 worker 的“只接受有界标量”判非法。修复：计划阶段按绑定工作流声明的槽位裁剪输入，**空值可选槽直接不发**；必需的槽位缺失则计划期就给出 `EXPLAINER_WORKFLOW_INPUT_UNRESOLVED` 并列出缺哪几个，而不是排队后失败。

**同时修正的审计脚本自身缺陷（否则结论会失真）**

**实测发现并修掉的两个缺陷（都属于“回溯代码后能优化的直接优化”）**

1. **成片画布忽略 edition，1080p 素材被压成 480p**：`make_composition_render_handler` 构建 manifest 时**没传** `width/height`，于是回退到 `AspectRatio.pixels` —— 一个模块级、在 import 时用 `DEFAULT_GENERATION_HEIGHT=480` 算好的代理尺寸，**既不读 edition 也不读配置的 `explainer_generation_height`**。而同一个管线生成的画面卡（`-card.mp4`）用的是 `primary_edition["width"]/["height"]`＝1920×1080，52 个镜头全部是 1080p。于是最后一步把真实 1080p 细节丢掉了，并依赖一个本机根本跑不起来的“后续超分”步骤。修复：新增 `_render_canvas()`，画布＝edition 的画布、并以**真实源片最高高度**为上限（源片只有 480p 时仍然按平台代理几何渲染，不无中生有地放大），渲染行的 `validation_json` 记录 `canvas` 与 `canvas_source`。实测：854×480 → **1920×1080**，码率 30.9 MB → 51.5 MB，帧数与时长不变（10148 帧 / 405.96 s）。
2. **混音把「绝对定位的旁白」又拼接了一次 → 82 % 成片是数字静音**：每个旁白片段已经用 `adelay` 定位到自己的 `sample_start`，而 `build_mix_command` 随后把 52 条已定位的轨道 **concat** 起来，等于把每个片段的绝对偏移在前面积累之上又叠加一遍。实测：成片 405.96 s 里 **333.9 s（82.3 %）低于 −45 dB**，52 条旁白里**只有 9 条可听见**，而 52 个源 WAV 逐个测过都含连续语音（mean −37…−18 dB，内部无 ≥0.6 s 静音）。修复：声明式音频路径改用 `amix(duration=longest, normalize=False)` 求和（旧式“按顺序给出的整段文件”路径仍用 concat，因为那种调用里顺序**就是**布局）。实测：静音段 9 段/82.3 % → **1 段/0.5 %**。新增真实 FFmpeg 回归用例 `test_real_ffmpeg_declared_narration_keeps_every_take_at_its_absolute_position`（断言 0 s 与 2 s 两段都出声、中间保持静音）。
3. **真峰值超出产品自述上限**：产品自述“−16 LUFS ±1、真峰值 ≤ −1 dBTP”（`DEFAULT_TRUE_PEAK_DBTP=-1.0`），而交付文件实测 **−0.7 dBTP**。原因是有损编码（AAC 192 kbps）在 loudnorm 之后又引入约 0.3 dB 的采样间峰值。修复：新增 `ENCODE_TRUE_PEAK_MARGIN_DB`，只对归一化器下调目标（0.5 dB → −0.9，1.0 dB → **−1.6 dBTP / −17.0 LUFS**），取 1.0 dB；两处合同现在都被交付文件本身满足，而不是被中间 PCM 满足。

25. **抽取阶段引用不存在的实体编号会让整条 `FACT_EXTRACT` 终止（本轮 8 篇复跑中 07/08 两篇命中）**：报错 `SCHEMA_INVALID: 引用了不存在的人物/实体：E004 / E006`，位置 `research.py::_resolve_entity_id`（同文件 `_resolve_claim_id` 是同类）。模型只抽取了 N 个实体却在别处引用 `E00N+1`，属**可恢复的模型错误**；当前零次重问，于是已经正确抽取的事实/事件/实体一起作废。修复方向（未做）：按文案既有模式给该阶段加**一次**带校验错误的重新询问——把“可用编号清单 + 你引用了不存在的 E004”作为纠正消息回给模型，仍失败则照旧报错（不静默丢弃引用）。同一文案在第 4 节第 12 项（分镜 `C007`）已记录过一次，属同一类缺口。
26. **故事时间口语写法仍会让整条 `FACT_EXTRACT` 终止（本轮 12 篇命中；服务端修复需要一次迁移）**：报错 `SCHEMA_INVALID: 日期无法解析：'今年三月'`，位置 `research.py::_apply_events → normalise_event_date(story_time_start)`。已经做过提示词侧规避（第 11 项，02 篇已因此通过），但模型仍会偶发写出相对时间。**服务端**正确做法是让故事时间接受口语文案并记录精度与原始字面量，而 `normalise_event_date()` 同时被 6 处调用（来源发布/更新日期的 2 处必须保持严格——原文就写着“silently losing a stated date is worse”）：4 处故事时间（`research.py:2078/2079/2136/2137`）需要走一个**新的**宽容入口。**阻塞点**：`explainer_events` 只有 `story_time_start/end/precision/calendar_system`，**没有**保存原始字面量的列，因此“保住原文”需要一次迁移（新增列或元数据列）+ 用例；本轮不做，留待下一轮，避免只做一半造成“静默丢日期”。
